The agenda

Three decisions,

Decision 01

Which identifier?

A — derived hash of lineage.
B — ULID plus a unique edge.
Or defer until E3 lands.

Decision 02

What does a report pin?

snapshot_id — convenient, and unverifiable after a rebuild.
(stage, observed_at) — reproducible from the archive.

Decision 03

Who proves it stays true?

A CI test that replays the archive, or a runbook step someone skips at 3 a.m.

For the room

We can settle 01 in ten minutes. 02 is the one that keeps the team aligned for the next two years — and it is the one nobody wrote down.

Framing

An identifier has three jobs.
We only argue about the first.

01
Identity

Point at exactly one state of one stage. Required by the fact-table foreign key and by lineage.

02
Dedupe

One row per change. A retry, a stale checkpoint or a re-run must not create a second version of the same observation.

03
Address

A report written last month still resolves today — after a rebuild, a correction, or a late-arriving capture.

Jobs 01 and 02 are database problems. Job 03 is a history problem — and it is the only place the two designs differ.

Real cardinality, real nulls, real invariants

Finding 01 · idempotency

Both schemes are idempotent.
The id is not why.

Failure pathAB
First observation1 row1 row
Identical publish, immediate retry1 row1 row
Rollback after header + fact0 rows0 rows
Process killed inside the transaction0 rows0 rows
Stale checkpoint, same edge2 rows2 rows
Same content, different parent2 rows2 rows
Second writer processrefusedrefused

“2 rows” in the two edge cases is the correct answer: those are two distinct observations, not a duplicate.

The mechanism

One commit, three writes

Header, fact rows and checkpoint move together. A retry sees all three or none — regardless of how the id was minted.

Idempotency lives in the transaction, not in the identifier.

For the room

Was anyone relying on the id for duplicate protection? If so, that belief is now measured, not assumed.

Finding 02 · the publish

Five moves. One whistle.

01 · BEGINopen transaction
02 · headerON CONFLICT DO NOTHING
03 · fact20 rows, only if new
04 · checkpointfingerprint + id
05 · COMMITall or nothing
Kill after 01–02

Nothing committed

The header write is invisible. Retry inserts once. Measured: 0 rows.

Kill after 03–04

Still nothing

Fact and checkpoint die with the transaction. Retry sees the old checkpoint and proceeds.

Kill after 05

A complete snapshot

The checkpoint already points at it. Retry returns no_change in ~5 ms.

There is no partial state to clean up — which is why the recovery runbook is three lines, not three pages.

A and B both return 1.

SQL compares NULLs as unknown, so the pair (NULL, fp) never collides with itself. The database is correct; the schema is wrong.

The rule

Sentinel, never NULL

parent_snapshot_id VARCHAR NOT NULL DEFAULT 'genesis'. The root is deduped by the same constraint as every other edge.

For the room

This is the only failure in the set with no error and no warning. Shall we add it to the schema review checklist?

Across scales

Why A moves: the id is a hash of the parent. A new node in the middle changes the parent of every child after it. Measured: 5 of 5.

Why B moves: the ids are random by construction. Replaying produces new names. Measured: 5 of 5.

In both schemes, a report pinned to snapshot_id returns 0 rows. Pinned to (stage, observed_at), both return 20.

Discussion · dead ends

Three tempting shortcuts
that don't survive history.

ProposalWhy it feels rightMeasured failure
Hash the content only “Same data, same row.” A → B → A collapses to 2 rows; the revert is erased.
Hash content + parent “The chain gives us reproducibility.” One backfill changes 5 / 5 downstream ids. It reproduces only an identical replay.
Store the snapshot id in the report “Pinning makes the report immutable.” 0 rows after a rebuild in B; 0 rows after a backfill in both.

The id is lineage. The observation is address.

Every shortcut above tries to make one value do both jobs. That works only while history is append-only and never corrected.

We already know corrections happen — the reason we keep raw is that the source changes.

Full time · recommendation

Take the ULID.
Stop treating it as an address.

All eight idempotency cases and all seven integrity checks pass for both schemes. The only difference that survives scrutiny is exact-replay id equality — a property that a single backfilled observation destroys.

The tie therefore breaks on what remains: shorter key, time-sortable, no dependence on chain position, and no hash of the parent to reason about.

+6.2%
storage · ≈ +10% median insert · −11 bytes per id

Cost accepted. None of it changes a query result.

Four conditions, non-negotiable
01  parent_snapshot_id NOT NULL DEFAULT 'genesis'
02  UNIQUE (parent_snapshot_id, content_fingerprint)
03  Reports pin (stage, observed_at); no stored snapshot_id outside the warehouse
04  CI replays the archive and asserts the (stage, observed_at) → content map
For the room

Condition 03 is the real decision. If we cannot commit to it, the honest answer is A — and then we accept that a backfill breaks pinned reports anyway.

Guardrail

Replay test asserts content, not ids

The old test compared snapshot_id sets. Under B that test must compare (stage, observed_at, content_fingerprint) — otherwise it fails for the wrong reason.
