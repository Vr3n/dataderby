Storage · what lands in DuckDB

One header.
Forty facts.

1snapshot header
20team facts, 60 measures each
20standings facts, 30 measures each
Why one transaction: a half-written snapshot is worse than none, because a chart would read a partial table as the truth. Facts and header commit together, or the database does not change. The fingerprint is a SHA-256 over the canonical content, so the same content always produces the same identity.

All of it commits in one transaction. A reader sees the full table or nothing. The header carries a 64-character SHA-256 content fingerprint.

Behaviour

Run it twice.
Write once.

same content, new capture time

checkpoint: no_change, attempts +1

Why the fingerprint ignores capture time: the source has no revision id. If we hashed the capture time, every retry would look like new data and the history would fill with duplicates. We hash content only, so an unchanged table is recognised as unchanged, however many times we look.

We measured it: the second publish returned no_change and the table still held one snapshot. The fingerprint ignores capture time, so retries are free.

First run · what broke

Four assumptions.
Four fixes.

1 · token

Not on require

The page now carries the token in its inline bootstrap.

2 · toggles

Silent copies

Selectors were title-cased; they matched nothing and every split read Overall.

3 · form

WWWWWL

The page sends upper case; the validator only accepted lower case.

4 · names

Man City ≠ Manchester City

Two labels for one team. teamName is canonical.

Why these four: each one was an assumption we had written into the code or the fixtures without evidence. Each produced a visible symptom only on real data, and each fix has a test that pins the corrected behaviour. None of them would have been found by the synthetic suite.

A fifth finding blocks everything else: the feed endpoint only answers inside the browser session. Slide 14.

Defect 2 · the silent bug

Three tables.
One table.

The selector asked for data-source="Home". The page has data-source="home". No match, no click, no error.

The first capture read Overall three times. Manchester City showed 8 played in every split. A20 blocked the publish, which is why we trust it.

Blocker · issue #14

A 200 that means 404.

Why this matters most: a 200 that means "not found" fools every status-code check. Our retry policy only sees 403 and non-200 codes, so this response is accepted as a body and then rejected as a gate page. The status code alone cannot be trusted; the body must be validated.

Plain HTTP to the feed returns status 200 with a short HTML page: "The page you requested does not exist."

The same URL returns JSON when the site's own page calls it. Copying cookies out of the browser does not help. The verified session is the transport.

Consequence: dataderby run cannot fetch live feeds yet. The capture script works because it fetches inside the page.
