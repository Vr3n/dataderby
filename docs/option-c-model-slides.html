P 01/ MODEL PROPOSAL / DATADERBY

Snapshot fact
for measures,
SCD Type 2 for identity.

A proposal to split the two rates of change in the football competition dataset — so that this season's numbers stop paying rent on last season's team name.

The claim

Two tables, two clocks, one join.

Measures append forever and never mutate. Identity versions only when it actually changes.

The stake

This is the shape every query will assume.

Locking it wrong means rewriting the marts, the tests and the deltas.

What I want from this deck

Sign-off on the model, not the code.

Four decisions and eight failure modes. Agree on those and the build is mechanical.

P 02/ THE PROBLEM

Two things in one row,
changing at wildly different rates.

Clock A · the measures

Points, goals, xG, ratings

Cumulative and monotonic in practice. Effectively every team changes on every matchday. 20 teams × ~50 windows = ~1,000 distinct states a season.

Clock B · the identity

Name, league, sponsor, badge

Changes a handful of times a season across the entire league — a rebrand, a promotion, a stadium move. ~2–4 rows a season, league-wide.

The failure of the single-table model

Version the measures and the name survives for 50 windows a season.

You pay the storage and the mutation cost of the fast clock, you inherit none of the cleanliness of the slow one, and you still cannot answer “what was this team called when it earned those points?” any more easily than before. You get the worst of both.

The fix is not a better single table. It is refusing to put two clocks in one table.

P 03/ GRAIN FIRST

Declare the grain before anything else.

Kimball's first rule, and the one that decides every query we will ever write. Three tables, three grains, and no two of them are the same — that is the point.

Header

competition_snapshot

one row = one accepted observation

The cohort. 20 teams observed together, validated together, published together or not at all.

Fact

fact_team_snapshot

one row = one team's measures
at one accepted observation

Append-only. Never updated, never deleted. This is the historical record.

Dimension

dim_team

one row = one team identity
valid over a time interval

Type 2. A new row only when a tracked attribute genuinely changes.

The test every proposed column must pass

“Does this value describe the team identity, or the team's performance in a competition season?” Identity goes to the dimension. Performance goes to the fact. There is no third answer, and any column that seems to need one is a modelling smell worth a conversation.

Why the fact keeps team_id too

Denormalising the natural key onto the fact is deliberate. It makes the fact self-describing — readable and testable without the dimension — and it lets us rebuild the dimension from the fact later. The surrogate key stays for joining.

Why not fold identity into the fact

Because then the name is a measure. Every window would produce a new “version” of Atlético Madrid that did not change, and the history would be noise dressed as change.

P 05/ DDL

The actual DDL, DuckDB.

-- ──────────────────────────────── the cohort ────────────────────────────────
CREATE TABLE competition_snapshot (
    snapshot_id        VARCHAR   PRIMARY KEY,   -- ours, never derived from a date
    tournament_id      INTEGER   NOT NULL,
    season_key         VARCHAR   NOT NULL,   -- '2026-2027', never a bare year
    stage_id           INTEGER,
    observed_at        TIMESTAMPTZ NOT NULL,  -- when we saw the source
    accepted_at        TIMESTAMPTZ NOT NULL,  -- when we published it
    source_fingerprint VARCHAR   NOT NULL,
    status             VARCHAR   NOT NULL    -- candidate | accepted | rejected
);

-- ──────────────────────────── the measures (append-only) ─────────────────────
CREATE TABLE fact_team_snapshot (
    snapshot_id   VARCHAR NOT NULL,
    team_sk       VARCHAR NOT NULL,             -- surrogate key into dim_team
    team_id       INTEGER NOT NULL,             -- natural key, kept for rebuilds
    ranking       INTEGER,
    rating        DECIMAL(4,2),
    points        INTEGER,
    goals_for     INTEGER,
    goals_against INTEGER,
    xg_for        DECIMAL(6,2),
    xg_against    DECIMAL(6,2),
    PRIMARY KEY (snapshot_id, team_sk),
    CHECK (goals_for >= 0 AND goals_against >= 0)
);

-- ──────────────────────────── the identity (Type 2) ──────────────────────────
CREATE TABLE dim_team (
    team_sk        VARCHAR PRIMARY KEY,          -- deterministic hash, see P 13
    team_id        INTEGER NOT NULL,
    team_name      VARCHAR NOT NULL,
    short_name     VARCHAR,
    league_name    VARCHAR,
    country        VARCHAR,
    attribute_hash VARCHAR NOT NULL,          -- change detection
    valid_from     TIMESTAMPTZ NOT NULL,        -- half-open  [valid_from, valid_to)
    valid_to       TIMESTAMPTZ,                     -- NULL = still current
    is_current     BOOLEAN NOT NULL,            -- derived, denormalised for speed
    UNIQUE (team_id, valid_from)
);

note — DuckDB parses FOREIGN KEY but does not enforce it. Referential integrity is a test we write, not a constraint we declare. See P 18.

P 06/ DATA FLOW

Where the two tables are written.

The important structural fact: the dimension is not on the hot path. It is touched on a small minority of runs, and the fact is written on all of them.

01Fixture window closes. A matchday has finished; the source may now have new numbers.
▼
02Gate-aware fetch. curl_cffi + Chrome TLS, cookie session, bounded backoff. Returns raw JSON or fails loudly.
▼
03Immutable raw capture + manifest. Payload sha256, run_id, HTTP status, parser version. Never mutated. Replayable.
▼
04Parse → validate → candidate cohort. pydantic on the envelope, pandera on the table. Expected team count, sections agree, ranges plausible.
▼
05Resolve identity. Compare each team's tracked attributes against its current dim_team version. Usually: nothing happens. dim_team
▼
06Insert fact rows. 20 rows, one per team, all sharing one snapshot_id. Append-only — no update path exists. fact_team_snapshot
▼
07Publish the cohort in one transaction. Header + fact rows + any dimension versions commit together, or not at all. competition_snapshot
▼
08Advance the checkpoint. last_committed_fingerprint moves only now. A crash before this line reprocesses cleanly.
▼
09Marts refresh. Everything downstream is a view over the two tables — no third copy of the truth.
P 07/ THE COMMON CASE

What 95% of runs actually execute.

A NORMAL RUN — MEASURES MOVED, IDENTITY DID NOT

-- one statement. no update. no merge. no delete.
INSERT INTO fact_team_snapshot BY NAME
SELECT snapshot_id, team_sk, team_id,
       ranking, rating, points,
       goals_for, goals_against, xg_for, xg_against
FROM staging_team_measures
WHERE run_id = 'run_0187';
  • Insert-only, so retries are free
  • No concurrency problem — nothing contends on a row
  • No dimension write, so no dimension history churn
  • Fully replayable from the raw capture

A CHANGE RUN — AN ATTRIBUTE ACTUALLY DIFFERS

-- close the version that was true until now
UPDATE dim_team
   SET valid_to   = :observed_at,
       is_current = false
 WHERE team_id = :team_id
   AND is_current;

-- open the version that is true from now on
INSERT INTO dim_team
  (team_sk, team_id, team_name, short_name, league_name,
   country, attribute_hash, valid_from, valid_to, is_current)
VALUES
  (:new_sk, :team_id, :name, :short, :league,
   :country, :new_hash, :observed_at, NULL, true);
  • Two statements, so it must be in one transaction
  • Stateful — re-running it naively is not idempotent. P 14 fixes this.
  • The only place in the system where a row is mutated

the asymmetry is the whole design — the fast path stays boring

Read the second lane

Six observations, one version. Betis never produces dimension churn — which is the point of separating the two clocks. A naive merge would have created six.

Closed

valid_to = observed_at, is_current = false. The row is not deleted — it is now a statement about the past.

Opened

New surrogate key, same team_id, valid_to = NULL, is_current = true.

Untouched

Betis, every fact row, and every pre-MD-15 measure. The blast radius of a rename is two rows.

the boundary is exactly observed_at of the run that saw the change — the same instant its fact rows carry

P 10/ THE JOIN

Reading it back: the temporal join.

POINT-IN-TIME — CORRECT

SELECT f.snapshot_id, f.points, d.team_name
FROM fact_team_snapshot f
JOIN dim_team d
  ON d.team_id  = f.team_id
 AND f.observed_at >= d.valid_from
 AND (d.valid_to IS NULL
      OR f.observed_at < d.valid_to);

Half-open intervals [valid_from, valid_to) mean no instant is matched twice and no instant falls through a gap. The IS NULL branch is not optional — see P 18.

THE BUG EVERYONE WRITES FIRST

-- looks right. silently drops every current row.
SELECT f.snapshot_id, f.points, d.team_name
FROM fact_team_snapshot f
JOIN dim_team d
  ON d.team_id  = f.team_id
 AND f.observed_at >= d.valid_from
 AND f.observed_at <  d.valid_to;  -- NULL < x is NULL → no match

Because the open version has valid_to IS NULL, the comparison is unknown and the row vanishes. Every “latest state” query silently returns yesterday. This is the most common SCD2 production bug, and it fails quietly.

The alternative, and why I still prefer NULL

A sentinel valid_to = '9999-12-31' makes the join NULL-free and is what many warehouses do. It costs a magic value that leaks into every consumer, and it forces a decision about whether is_current or the sentinel is authoritative. I prefer NULL plus is_current, both derived from the same source, both covered by tests.

P 11/ THE QUERY SURFACE

What consumers actually get.

No consumer joins the two tables by hand. Everything downstream is a view over the same two tables — no third copy of the truth. 

-- 1 · latest accepted state · the default read
CREATE OR REPLACE VIEW latest_team_state AS
SELECT f.*, d.team_name, d.league_name,
       s.observed_at, s.season_key
FROM fact_team_snapshot f
JOIN dim_team d ON d.team_id = f.team_id
   AND f.observed_at >= d.valid_from
   AND (d.valid_to IS NULL OR f.observed_at < d.valid_to)
JOIN competition_snapshot s USING (snapshot_id)
WHERE s.status = 'accepted'
QUALIFY row_number() OVER (
   PARTITION BY s.tournament_id, s.season_key, f.team_id
   ORDER BY s.observed_at DESC) = 1;
-- 2 · how the table itself changed
CREATE OR REPLACE VIEW team_snapshot_delta AS
SELECT team_id, observed_at,
       points    - lag(points)    OVER w AS points_delta,
       goals_for - lag(goals_for) OVER w AS goals_delta
FROM latest_team_state
WINDOW w AS (PARTITION BY team_id
            ORDER BY observed_at);
team_snapshot_history

Every version of a team's measures.

dim_team_current

Today's team list, one row each.

snapshot_completeness

Teams captured vs expected, per cohort.

source_freshness

Expected window vs observed_at.

caveat, stated up front — delta views are derived and approximate; never offer them for rankings, ratios or per-90 rates.

P 12/ SIZING

The numbers, so nobody argues about scale.

The honest reading

At this scale every option fits in memory. Storage is not the argument, and I am not going to pretend it is. The argument is mutation and query clarity: one row mutated 1,000 times a season is a table with a lifecycle; 20 rows mutated about three times is a lookup that behaves like a lookup.

Where the sizing does bite

DuckDB is single-node and this is at most a decade of data per competition. If we ever cover many competitions and divisions, the fact grows linearly while the dimension stays flat — which is exactly the shape you want when it does start to matter.

P 13/ KEYS

Surrogate keys: deterministic, not sequential.

Rejected — a sequence 
CREATE SEQUENCE team_sk_seq;
-- nextval() per new version
  • Rebuilding the dimension assigns different keys than last time
  • Two environments disagree on the same data, so a diff is meaningless
  • Any replay changes the identity of a historical row — exactly what Type 2 exists to prevent
Adopted — a deterministic hash 
SELECT 't_' || team_id || '_'
    || substr(md5(team_id || '|' || valid_from), 1, 4)
  AS team_sk;
  • A full rebuild is byte-identical to the previous build
  • Two environments agree, so a diff is meaningful
  • Idempotency becomes testable rather than aspirational
  • Readable, and stable as long as the natural key is stable
The assumption this rests on

This only works if team_id is stable and immutable. That is an open question against the source (P 22) — if the provider ever reuses an id for a different club, the natural key is not a key and we need a different binding.

P 14/ IDEMPOTENCY

The part that decides whether this is safe to operate.

A stateful UPDATE + INSERT is correct once and wrong twice. Run it again and you have a zero-length version, then another. This is the single biggest hidden cost of Type 2 — and it has a standard answer.

Mutate — the naive version
  • Re-running the same capture inserts a duplicate version
  • Recovery requires knowing exactly what you already wrote
  • A failure mid-way leaves an orphaned open version
  • Reproducing a historical state means replaying the writes in order

Viable, but only with a lock, a state table and careful ordering. We would be building all three to solve a problem we could delete instead.

Derive — the version I want

Treat dim_team as a derived table. Rebuild it from the accepted facts, deterministically, every time. 

-- identity observations come from the
-- accepted fact rows themselves
observed_attribute_change AS (
  SELECT team_id, observed_at,
         team_name, league_name,
         md5(...) AS attribute_hash
  FROM fact_team_snapshot f
  JOIN competition_snapshot USING (snapshot_id)
  WHERE status = 'accepted'
)
-- keep where the hash changed, then
-- lead() to obtain the next valid_from
  • Re-running produces the same rows, so replay is free
  • Repairing a bad parse is a rebuild, not a data migration
  • The dimension becomes a pure function of accepted data

the price of deriving — the attribute history must be present on the fact rows, so the fact carries the identity fields it observed

P 15/ THE SUBTLEST DECISION

Not every difference is a change.

This is where bad historical models are made. If the source fixes a typo and we record that as a rebrand, we have invented a corporate event that never happened — and it is in the history forever.

Correction → Type 1, fix in place

“Atltico Madrid” → “Atlético Madrid”

  • A typo, an accent, a whitespace difference
  • The world never changed; only our knowledge of it did
  • No new version. No new validity interval.
  • Otherwise every consumer sees a phantom rename
Change → Type 2, new version

“Atlético Madrid” → “Atlético Madrid CF”

  • A rebrand, a rename, a promotion between divisions
  • The world changed at a point in time that we observed
  • New version, and the old rows keep the old name
  • The history is the product
So how do we tell them apart — this is a decision we have to make deliberately

A · NORMALISE, THEN COMPARE

Trim, unicode-fold and casefold before hashing. Kills the cheap false positives; cannot catch a real typo fix.

B · TRACK A VERSION HINT

If the source exposes a stable club id plus a separate display field, treat display-only changes as Type 1 and id changes as Type 2.

C · MANUAL OVERRIDE REGISTRY

A small reviewed table of “this diff is a correction, not a change”. Honest, and cheap at this scale.

My recommendation: A + C. Normalise automatically, and keep a reviewed override list for the handful of cases a year that need a human call.

P 16/ THE CASE FOR

What this buys us.

01 · Correctness

Historical truth, not a rewritten past.

A fact row observed under the old name keeps the old name forever. Every other model either loses that or fakes it.

02 · Operational safety

The hot path is append-only.

Retries, concurrency and crash recovery are trivial where it matters — on the path that runs every matchday.

03 · Query clarity

“Latest state” is a defined concept.

One view, one meaning, and a cohort that is complete by construction. Analysts stop guessing which 20 rows are the real ones.

04 · One obvious way

It is what every engineer already knows.

A Kimball dimension plus a snapshot fact. New contributors read it without a briefing, and dbt or SQLMesh can take it over later without a rewrite.

05 · Growth

Cost tracks what actually changes.

Adding a competition adds facts, not dimension churn. The slow table stays slow.

06 · Testability

The invariants are assertable.

No overlaps, no gaps, exactly one current row, every fact resolves to exactly one version. These are checks, not hopes.

P 17/ THE CASE AGAINST

What it costs.

Stated plainly, because a proposal that only lists benefits is a proposal nobody should trust.

01 · One more table, one more concept

In v1 it is genuinely more to hold in your head. Snapshot-fact-only is simpler, and I would accept it as the minimum.

02 · Mutation enters the system

Every “we never UPDATE” claim now has an exception. It is one table, but it is a real architectural exception that must be documented and tested.

03 · Validity intervals are inferred, not known

valid_from is when we saw the change, not when it happened. The source gives us no publication timestamp. That imprecision is unavoidable and must be documented, not hidden.

04 · The join is a footgun

The NULL valid_to trap (P 10) will be written by someone within a month of this shipping. Mitigated by views, not by discipline.

05 · Correction-versus-change is a judgement call

We cannot derive it from the data. It needs a rule, an override list and a human. That is ongoing cost, not one-off cost.

06 · Restatements move the boundaries

If we rebuild after a late-arriving correction, the dimension's boundaries change and any query pinned to them changes meaning. P 18 turns this into a test.

The alternative I would accept if you push back

Ship the snapshot fact alone in v1. Keep identity as plain columns on the fact. Add the dimension when the first rename, promotion or relegation actually lands — and design the fact now so that adding the dimension later is a view change, not a migration. That is the low-regret path, and I am happy to take it.

P 18/ WHAT TO BE CAREFUL ABOUT

Eight ways this model breaks
in production.

Each of these has been seen in the wild. Each one fails quietly, which is why each one gets an assertion rather than a note in a document.

01 · The NULL valid_to join

f.observed_at < d.valid_to evaluates to NULL for the open version, so every “current” row silently disappears. → add OR d.valid_to IS NULL

02 · Overlapping or gapped intervals

A crashed transaction, a backfill, or a boundary computed from the wrong clock leaves two versions true at once, or a hole where none should exist. → assert no overlap and no gap per team_id

03 · Two current rows for one team

The classic SCD2 bug. Two rows with valid_to IS NULL make every latest-state query return the team twice, doubling aggregates. → assert count(*) = 1 per team_id where is_current

04 · is_current disagreeing with valid_to

Two representations of the same fact will diverge the first time someone writes one without the other. → derive both from one column; assert equivalence

05 · Which clock bounds validity

Mixing observed_at on the fact with accepted_at on the dimension yields a model where a restatement changes which version a historical fact resolves to. → one clock, documented, asserted

06 · Unenforced referential integrity

DuckDB accepts FOREIGN KEY but does not enforce it. A parse bug can write a fact row whose team_sk does not exist, and nothing complains. → assert an anti-join returns zero

07 · Spurious versions from cosmetic drift

A trailing space, a Unicode normalisation difference or a case change creates a “rename” that never happened. → normalise before hashing, and review the first month of diffs by hand

08 · Restatement rewrites the past

A late correction re-derives the dimension and moves a boundary that an earlier report was built on. → pin reports to snapshot_id, not to wall-clock time

P 19/ THE CONTRACT

The invariants, as executable tests.

If this model ships, these six assertions run on every publish — not in a quarterly audit. They are the actual specification; everything else is implementation.

#InvariantAssertionOn failure
I1Exactly one current version per teamno team_id has more than one row with is_currentblock publish
I2No overlapping validityno two versions of a team hold the same instantblock publish
I3No gaps on the real lineeach valid_to equals the next valid_fromwarn
I4Every fact resolves to exactly one versionthe temporal join yields one row per fact rowblock publish
I5Referential integritythe fact → dim anti-join is emptyblock publish
I6Apply-once is safereapplying the same capture changes nothingblock publish
I6 is the one that earns the design

If dim_team is derived (P 14), I6 is checked by rebuilding and diffing against the committed state. Two identical tables means replay is safe — and that is the property that makes a 3 a.m. recovery a non-event.

Why I3 only warns

A gap can be legitimate — a team that leaves the competition and returns, or a season with a mid-year format change. It deserves a human look, not a blocked pipeline. Overlap is never legitimate; a gap sometimes is.

The two that deserve a real defence

Snapshot fact only is a legitimate v1 and I would ship it — it defers the dimension without blocking it. System-versioned is the correct pattern in the wrong engine: DuckDB does not implement it, and adopting it means adopting a server database against the local-first decision.

And the one that is a trap

One wide table is the fastest thing to build today, and the reason this deck exists. It cannot answer “what was this team called when it earned those points”, and it will not be able to later, because the evidence has been overwritten.

P 21/ ROLLOUT

Two stages, and nobody's query breaks.

Stage 1 · v1, the low-regret build
  • Snapshot fact, wide, append-only
  • Identity carried as plain columns on the fact row
  • latest_team_state published as a view
  • Cohort validation and atomic publish
  • Raw captures, manifest, checkpoint

This is already the correct model. It simply does not yet know that identity is a separate clock.

Stage 2 · add the dimension behind the view
  • Build dim_team from the attribute columns already on the fact
  • Swap latest_team_state over to the temporal join
  • Drop the redundant attributes from the fact surface, keep them underneath
  • Add invariants I1–I6 to the publish step
  • Add dim_team_history and point-in-time reads

Because the identity fields were on the fact all along, stage 2 is a view change plus a derived table. No migration, no backfill, no lost history.

The trigger to actually do stage 2

The first rename, promotion, relegation or rebrand observed in the wild — or the first time someone asks a question the single table cannot answer. Until then, stage 1 is not a compromise; it is the right amount of model.

  2. D2  Which attributes count as identity — name only, or name + league + country?

  2. Does the payload expose a publication timestamp at all?
  3. Is a rename distinguishable from a typo correction?
  4. How many independent sections must agree before a cohort is complete?
  5. Is league membership on the team payload, or only in the table probe?
The ask

Approve D1–D4 and the eight failure modes in P 18. Agree that the identity attributes live on the fact from day one, whichever stage we start at. Everything after that is mechanical.
