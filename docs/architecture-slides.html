P 02/ THE PROBLEM

One sentence, because
everything else is a consequence of it.

“At each accepted observation point, the source reports a table of teams and a set of cumulative statistics for those teams. We want to retain every reported state so the same team can be compared with itself and with others across time.”

Property 01

Cumulative,
not per-event

Goals-for is a season-to-date total. A difference between snapshots bounds combined activity; it cannot be attributed to a match unless exactly one sits between them.

Property 02

Event-driven,
irregular cadence

Triggers are fixtures finishing, and the source publishes late and in batches. Kimball's periodic snapshot assumes a fixed, dense period. We have neither.

Property 03

Thin and
hostile source

No update timestamp. No ETag. No revision id. An anti-bot gate. Possible silent corrections. We cannot ask the source what changed.

P 03/ CREDIT WHERE DUE

The field guide is better
than most published advice.

These four claims I would defend in review, and they should survive into the implementation unchanged.

The asymmetry

A changed table may imply ready details.
An unchanged table proves nothing.

Most “hash the page” advice treats a stable hash as safe-to-skip. It is not, unless you have verified the reverse implication against the source.

Atomic publication

Eighteen of twenty teams
must never present as “latest”.

An incomplete capture would read as a smaller league. The cohort is the unit of publication, not the row.

Operational honesty

Run outcome ≠ data outcome.

“Checked the source, nothing new” is a success. Conflating it with “scrape failed” is what makes dashboards lie.

Correctness

Refusing to invent match-level attribution.

Deltas between cumulative totals are derived, approximate, and meaningless for rankings, ratios and per-90 rates.

P 04/ WHAT THE LITERATURE ADDS

Four named patterns the guide
re-derives without naming.

Two of these change the design. The other two change how much code we own.

Gap 01 · shapes Decision 1

SCD Type 2 is a solved problem

The guide builds versioning by hand. dbt snapshot emits dbt_valid_from / dbt_valid_to / dbt_scd_id from two built-in strategies; SQLMesh ships an SCD_TYPE_2 model kind. Choose it, don't invent it.

Gap 02 · shapes Decision 1

Identity and measures
change at different rates

Team names, league membership and promotion are the actual slowly-changing dimension. Season-to-date metrics are the fact. The guide versions both on one row — worst of both.

Gap 03 · shapes the cross-cutting layer

Fingerprint the logic, not just the source

SQLMesh fingerprints a model over its logic and its upstream dependencies. Without that, fixing the parser leaves stale derived tables with no signal that they are stale.

Gap 04 · shapes Decisions 2–4

The guide never asks
build or buy

dlt already does schema inference and evolution, incremental state, nested-JSON normalisation and loads to DuckDB. The guide hand-rolls all of it — §3.6 and §5.2 — without noting the alternative.

P 05/ SETTLED

Not up for debate.

Supported by both inputs. Every decision below has to live with these.

  1. 01 Raw evidence is immutable and append-only.
  2. 02 Derived layers are rebuildable from raw.
  3. 03 Publication is atomic per observation.
  4. 04 The checkpoint advances only after acceptance.
  5. 05 A team is identified by a stable source id, never a name.
  1. 06 Missing is not zero.
  2. 07 A season is (tournament, season) — never a calendar year.
  3. 08 Deltas are derived, flagged, never for ordinal or ratio metrics.
  4. 09 Every observation records when it was observed, in UTC.
  5. — plus: raw is never the input to a query; marts are never the only copy.
FORK 01/ 04 / HISTORY MODEL

How do we model the history?

Three axes hide inside this question, and conflating them is what makes it feel hard.

Axis 1

The mechanism

Immutable rows · mutable row + validity period · or the database doing it for you.

Axis 2

The shape

Wide — a column per metric · long — a row per metric · or a hybrid of the two.

Axis 3

What gets versioned

Measures only · or measures and team attributes, at their own separate rates.

Option A · Axis 1

Immutable snapshot fact

One row per team per accepted observation. A header carries the cohort. Nothing is ever updated.

  • Perfect audit trail; corrections appear as a visible change
  • Insert-only → retries and concurrency are trivially safe
  • The observation cohort is explicit, so incompleteness is a validation failure
  • “Current value” needs a window function or a view
  • Team attributes duplicate on every row
Option B · Axis 1

SCD Type 2 on the measures

Mutate in place: close the old version with valid_to, insert a new one. What dbt and SQLMesh produce.

  • Idiomatic point-in-time queries
  • Compact — one row per change, not per observation
  • Loses the observation cohort entirely
  • Our measures change for nearly every team every matchday → storage of the snapshot model plus mutation
  • No trusted updated_at to drive the timestamp strategy
FORK 01/ 04 / HISTORY MODEL

Two more options, and a verdict.

Option C · Axis 1 + 3

Snapshot fact for measures,
SCD2 for the team dimension

Split the two rates of change. Measures append forever; names and league membership version independently.

  • Each thing versioned at its natural rate — names cost ~20 rows a season
  • Fact stays append-only where mutation would hurt
  • Point-in-time team names for free
  • Literally what dimensional modelling prescribes
  • One more table and concept in v1
Option D · Axis 1

Let the database keep history

SQL:2011 system-versioned temporal tables. FOR SYSTEM_TIME AS OF …

  • Point-in-time queries in one clause; compliance-grade
  • DuckDB does not implement it — adopting it means a server database
  • Versions transaction time, not valid time — and our valid time is the thing we care about
  • Microsoft's own docs warn it is unsuitable when loading is significantly delayed — which is exactly our case

VERDICT: BORROW THE CONCEPT, NOT THE ENGINE

Axis 2 · recommendation

Hybrid shape

Keep the fact wide for the few stable metrics we actually model — points, goals, xG, ratings. Put the situational and positional tail — potentially hundreds of categories — in a long child table keyed by (snapshot_id, section, view, category, direction). That child is a different grain and Kimball says to declare it as such, not smuggle it into the fact row.

Decision 01 · recommendation

Take Option C.

Immutable snapshot fact for measures, a small SCD Type 2 dimension for team attributes, wide core with a long child table for the tail. It is the only option where each thing is versioned at its own rate, and it keeps the guide's two strongest ideas — explicit cohort, atomic publication — while staying append-only where mutation would hurt. Minimum viable version: Option A alone, with the dimension table sketched but not populated.

FORK 02/ 04 / INGEST BOUNDARY

Where does the ingest layer's
boundary sit?

Ingest is where the irreducibly-bespoke work lives and most of the boilerplate lives. Put the line in the wrong place and you either hand-maintain boilerplate forever, or fight a library to do the one thing only this source needs.

Option A

Hand-roll everything

  • Total control over the gate, cookies, backoff, quirks
  • One dependency fewer
  • We re-implement schema evolution, incremental state, normalisation, load bookkeeping
  • Schema drift is the part people get wrong — and the part a library has already solved
Option C

dlt end to end, ingestion included

  • Least code overall — if the source were well-behaved
  • Our source is hostile, not paginated. The problem is TLS fingerprinting, not paging
  • dlt's HTTP layer is not curl_cffi with Chrome impersonation
  • Bolting that in means fighting the abstraction — which removes the reason to use it

REVISIT IF A WELL-BEHAVED SECOND SOURCE APPEARS

Option B · Decision 02 recommendation

Hand-rolled client, library-owned loading.

We own extraction — the gate is bespoke and unavoidable. Start by writing rows with plain DuckDB SQL from pydantic-validated models; add dlt the moment the payload shape churns more than once or a second source appears. The boundary is the same either way — the client yields dicts — so this is a drop-in later, not a rewrite.

also considered and set aside: Scrapy (a framework for thousands of HTML pages, not a handful of gated JSON endpoints)

FORK 03/ 04 / RAW EVIDENCE

Where does the raw evidence live?

This layer has one job: given a bug in the field mapping, reproduce the accepted output without touching the source again. Scale check so nobody architects the wrong problem — one capture ≈ a few KB, a snapshot ≈ 9 requests, a season ≈ 40–60 windows. A few megabytes.

Option A · recommendation

Local immutable files + manifest

data/raw/tournament=4/season=2026-2027/
  observed_at=…Z_run=run_0187/
    manifest.json
    team_statistics__overall.json

  • Greppable, diffable, offline, zero infrastructure
  • Naturally replayable — the whole point
  • A retry producing a second file is correct: two attempts are two facts
  • No content-addressing — identical payloads stored twice
  • Durability is “whatever you back up”
Option B

Git scraping

A scheduled job commits each capture. Git becomes the append-only, content-addressed store — git log -p is your change history.

  • Immutable, deduplicated, diffable, backed up, portable — all free
  • Exactly our product goal (“when did this value change”) out of the box
  • Simon Willison hit our exact problem: Cloudflare blocked the GitHub Actions IP range, worked around with a Tailscale exit node
  • Actions cron is imprecise; our scheduling is fixture-driven
  • Committing derived data to git is a known anti-pattern
Option D

Object storage

The production answer — lifecycle rules, versioning, cheap. Solves a durability problem we do not have, at the cost of credentials and a network dependency in the hot loop. Steal the path convention, not the infrastructure.

Option E

Payloads in a database column

Named only because it is the tempting shortcut. It couples evidence to the warehouse lifecycle and makes a parser bug a database migration. Don't.

Decision 04 · recommendation

Plain Python + DuckDB for v1. Then adopt by trigger, not by preference.

A scheduled run_once(now) owns the fixture-window logic, a checkpoint table, and SQL views. Then: SQLMesh or dbt when the model layer outgrows a handful of views or SCD2 becomes routine — SQLMesh for fingerprint-driven rebuilds, dbt for the larger ecosystem. Dagster when there is a second source, a second consumer, or a backfill you would not dare run by hand.

Do not adopt Dagster and a transformation framework at the same time — that is two new mental models for one source.

X-CUT/ POINTS EVERY OPTION MUST ANSWER

Two fingerprints, three identities,
one honest clock.

Change detection — the guide has one; we need two

source_fingerprint / logic_fingerprint

source_fingerprint — canonicalised digest of the observed state: sorted by stable team id, key order normalised, volatile fields excluded. Decides append a new observation, or skip.

logic_fingerprint — a version stamp over parsing code, field mapping and schema version. Decides do derived tables need rebuilding. Without it, fixing the parser leaves stale derived data with no signal that it is stale.

Idempotency — three identities, à la the guide and dlt

run_id · capture_id · snapshot_id

A candidate whose source_fingerprint already exists as accepted for the same (tournament, season, stage) is a duplicate — rejected, not published. Raw may hold three captures for that state; the model holds one snapshot. This is what makes retries safe.

The honest clock — bi-temporal, as columns rather than as a database feature

fixture_end_expected_at  → from the fixture list
source_published_at     → UNAVAILABLE — leave null, do not invent it
observed_at              → our probe time, UTC
captured_at             → per byte-payload
accepted_at             → when the complete snapshot was published
valid_from / valid_to   → SCD2 dimension only

source_published_at being genuinely unavailable is itself a finding worth recording — it means “the source was late” can only ever be inferred from observed_at.

Observability — Monte Carlo's five pillars, borrowed as vocabulary because it is free

freshness · expected window vs observed_at    volume · teams captured vs expected    schema · fields added, removed, retyped    distribution · plausibility bounds    lineage · capture → staging → snapshot, and which parser version produced it. Tracked as rows in a ledger, not log lines — so “when did this last get a valid observation?” is a query.

PROBE/ NOT ANSWERABLE FROM THE LITERATURE

Eight things only the source
can tell us.

These gate the change-detection design in particular. Until #2 is measured, treat skipping the detail fetch as unsafe.

  1. 01 Is there a cheap league-table endpoint to act as the probe, or is the smallest request already the detail feed?
  2. 02 Does an unchanged table imply unchanged details? Hold the table fingerprint fixed across a fixture and see whether any detail field moves.
  3. 03 Does the source expose any update timestamp, ETag, or revision id? If yes, this gets much easier.
  4. 04 Are values ever corrected retroactively? Compare an accepted snapshot against a re-fetch days later.
  5. 05 Is teamId stable across seasons and competitions?
  6. 06 How long after a final whistle does the source publish? This sets the grace period and retry cadence.
  7. 07 What does the anti-bot gate look like now — TLS only, or cookie/session-bound? Determines whether the client can be stateless.
  8. 08 What is the real metric count across sections and views? Decides wide vs long for the tail.
