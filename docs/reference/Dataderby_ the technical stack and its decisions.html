Page 2 · The map

Four layers, four rules

Split the job so each part can fail alone. A crash in one layer must not damage another.

1 · Fetchcurl_cffi · Playwright for cookies

Writes raw files only. Never touches the database.

2 · Raw landingFiles on disk

Immutable. Partitioned by observed date.

3 · LoadPython + DuckDB

One writer. Stage, audit, then publish in one transaction.

4 · ServeSQL views

Latest, delta and freshness are views. No second copy of the truth.

Fetch only brings bytes home. It makes no decisions about the data.Raw files never change. They are the receipt we can read again.One process writes to DuckDB. It checks first. Then it publishes all or nothing.Views answer questions. They do not store another copy.

Page 3 · Fetching

curl or Playwright? Pick by the block, not by habit

Fingerprint = how a client says hello. A script’s hello looks different from a browser’s.

SituationToolCost
Endpoint answers a normal requestrequests or httpxCheapest. Start here.
403 until the TLS handshake looks like a browser’scurl_cffi with impersonate=“chrome”One process, no browser. Fast.
Needs JavaScript, or a cookie set by a page scriptPlaywright once, then give the cookies to curl_cffiA real browser: heavy and slow. Use it once per window.
Hard bot block or captchaStop. Ask for a licensed feed.Scraping is the wrong tool.

Fetcher rules: save raw bytes first, parse later · bounded retries with backoff and jitter · one request at a time · log every attempt in the ledger.

Most sites need nothing special. Try the cheap tool first.A TLS handshake has a recognisable “grip”. curl_cffi copies a real browser’s grip.Playwright is a full browser. It is slow, so use it for the cookie only.Know when to stop. A hard block is a licensing question, not an engineering one.Our recon notes say: TLS gate, cookie-bound gate, hard block. Plan: Playwright for the cookie, curl_cffi for the 9 requests. This is a hypothesis. Test it first.

Page 4 · Raw landing and partitions

A partition is a folder you can replay or delete as one unit

Choose the partition key by how you will replay and delete, not by how the data looks.

raw/  source=whoscored/    tournament=4/season=11213/stage=25662/      observed_date=2026-10-17/        run=0187/   manifest.json + 9 response files

Do not partition by team: 20 tiny files per run. Estimate: about 1,000 fact rows per competition-season. A DuckDB table needs no partitions yet.

Start with one landing folder.Source first. A second source gets its own branch.The competition ids come from the source, not from us.Partition by observed date. That is how we replay: by day.One run folder holds the manifest and every file. Delete the folder, and that attempt is undone.

Page 5 · Writing rows

INSERT, ON CONFLICT, MERGE: each has one job

MERGE can update. Our rule is that facts never change. So facts do not use it.

Bare INSERT, run twice2 rowsDuplicates. Not idempotent.
Primary key + INSERT againErrorLoud and safe.
ON CONFLICT DO NOTHING ×21 rowRetry changes nothing.
ON CONFLICT DO UPDATE99Value replaced.
MERGE INTOworksDuckDB 1.5.6 (added in 1.4.0).
ROLLBACKkeptEarlier rows stayed.
TablePatternWhy
snapshot, factINSERT … ON CONFLICT DO NOTHINGAppend-only. We never edit a fact.
checkpoint, team mapMERGE (or ON CONFLICT DO UPDATE)Current state. One row per key.
marts, derived tablesDELETE + INSERT in one transactionRebuild whole. Safe to repeat.
Tested. A bare INSERT repeats itself. A key stops it with an error.Tested. DO NOTHING makes a retry harmless. DO UPDATE replaces the value.Tested. MERGE works. A rollback leaves the old rows.Rule: facts only grow. State tables change. Derived tables are rebuilt.

Page 6 · Idempotency

Run it twice. Get the same database.

The id must come from the data, not from the clock. Then a retry builds the same id.

S1A = 10 · prev: none

id = hash(content + previous id)

S2A = 13 · prev: S1

Stored.

S2 retrysame content, same prev

Same id. No-op. Still 2 snapshots.

S3 revertA = 10 again · prev: S2

New id. Stored. 3 snapshots.

No chainid = hash(content)

S3 gets S1’s id. Silently dropped.

Layers: fetch writes a new file each time · parse is a pure function · publish uses a deterministic id · checkpoint uses MERGE.

Each snapshot id hashes its content and the id before it, like a git commit.Tested. A retry computes the same id, so ON CONFLICT DO NOTHING skips it.Tested. A revert has the same content but a different parent, so it is recorded.Tested. Without the chain, a revert was silently lost: 2 stored, 3 states happened. Proposal, tested on toy data.

Page 7 · Write, audit, publish

Stage it, check it, then publish in one transaction

Write-Audit-Publish: check the cake before it goes on the table.

-- 1 WRITE: stage the candidate. Nothing is published.CREATE TEMP TABLE stg AS SELECT * FROM read_json('run=0187/*.json');-- 2 AUDIT: every query must return 0 rowsSELECT team_id FROM stg GROUP BY 1 HAVING count(*) > 1;SELECT 1 WHERE (SELECT count(*) FROM stg) <> 20;-- 3 PUBLISH: all or nothingBEGIN;INSERT INTO competition_snapshot (...) VALUES (...) ON CONFLICT DO NOTHING;INSERT INTO fact_team_snapshot SELECT ... FROM stg ON CONFLICT DO NOTHING;MERGE INTO pipeline_checkpoint ...;COMMIT;

Tested: a second process that opened the same database file failed with “Could not set lock on file”. So: many fetchers, one loader.

Write: the candidate lives in a temp table. The live tables are untouched.Audit: each check is a query. Any row returned means stop.Publish: header, rows and checkpoint commit together. A crash before COMMIT leaves nothing.Design for the lock: fetchers write files. One loader writes the database. Sketch code, not final.

Page 8 · Managing partitions

Overwriting a partition is not automatically safe

A partition overwrite replaces files. It does not replace the folder. Know the difference.

First partitioned write2 foldersone folder per day
Rewrite, no optionErrorDirectory is not empty
OVERWRITE_OR_IGNORE, one dayOKsame-named file replaced, other day untouched
APPEND, run twice9 rowssource had 3: duplicates
Overwrite after 2 older files210 rowsexpected 10: stale files stayed

Safe pattern: write to a temp folder · check the row count · swap the folder · keep one file per partition · never mix APPEND with overwrite. A MotherDuck article says OVERWRITE_OR_IGNORE clears the whole directory. We saw otherwise on 1.5.6. Test on your version.

All tested on DuckDB 1.5.6. Writing partitioned data makes one folder per value.Overwrite replaces files with the same name. APPEND adds new files, so a retry doubles the rows.The worst case: old files with other names stay. 210 rows instead of 10, and no error.So an overwrite is idempotent only if you control the file names or delete the folder first.

Page 9 · The Python layer

Keep the middle pure. Keep the edges thin.

The more code is pure, the less you need to mock.

parse/ · validate/Pure functions

Same input, same output. Test them on saved raw files.

fetch/ · publish/The edges

The only code that touches the network and the database. Keep it small.

plan/ · ledger/run_once(now)

The clock is a parameter. Fixtures decide what is due. Every run writes a ledger row.

tests/Five must-haves

Publish twice = once · crash before COMMIT = nothing · revert is recorded · NULL is not zero · parser golden files.

Pure code is easy to test, so put the logic here.Side effects live at the edges. A thin edge has fewer bugs.Pass the time in. Then a test can pretend it is Sunday 9 pm.These five tests prove the guarantees. Tools: uv, ruff, mypy, pytest.
