01 / the question

An id has three jobs. We only ever argue about the first one.

job 01

Identity

Point at exactly one state of one stage. Required for the fact-table foreign key and for lineage.

job 02

Dedupe

One row per change. A retry, a stale checkpoint, or a re-run must not create a second version of the same observation.

job 03

Address

A report written last month still resolves today — after a rebuild, a backfill, or a correction to history.

Jobs 01 and 02 are database problems. Job 03 is a history problem — and it is the only one where the two schemes measurably differ.

03 / the candidates

Two designs, and a trap variant we built on purpose.

A · derived

Hash the lineage

snap_56822dad813380f4
27bbeae854b068d2

sha256(parent | stage | content)[:32]
Dedupe is the primary key. The id is the edge.

B · ULID

Name the row, constrain the edge

01M5A8AA42SDDVAQZX2Y48XJWG

UNIQUE(parent_snapshot_id, content_fingerprint)
Dedupe is a constraint. The id is just a name.

B-null · trap

Same, with a NULL root

parent = NULL

SQL treats NULLs as distinct in a UNIQUE constraint. The first observation can be inserted twice — measured: 2 rows.

All three share the same pipeline. B-null is not a candidate; it exists to price the most common way this design is implemented wrongly.

05 / idempotency

Both schemes are idempotent. The id is not why.

Failure pathAB
Identical publish, immediate retry1 row1 row
Rollback after header + fact0 rows0 rows
Process killed inside the transaction0 rows0 rows
Stale checkpoint, same edge2 rows2 rows
Same content, different parent2 rows2 rows
Second writer processrefusedrefused

“2 rows” in the two edge cases is the correct answer: those are two distinct observations, not a duplicate.

the mechanism

One commit, three writes

Header, fact rows and checkpoint move in a single transaction. A retry either sees all three or none of them — regardless of how the id was minted.

why the test matters

Revert is not a duplicate

S1state A
→
S2state B
→
S3state A again

Measured: 3 snapshots. A dedupe key on content alone would return 2 and silently lose the revert.

Idempotency lives in the transaction, not in the identifier.

06 / the trap

A unique constraint does not protect the first row if its parent is NULL.

-- the obvious implementation
CREATE TABLE competition_snapshot (
  snapshot_id         VARCHAR PRIMARY KEY,
  parent_snapshot_id  VARCHAR,          -- NULL for the first
  content_fingerprint VARCHAR NOT NULL,
  UNIQUE (parent_snapshot_id, content_fingerprint)
);
-- two inserts of the same first observation
INSERT ... (parent = NULL, fp = 'a91f…');
INSERT ... (parent = NULL, fp = 'a91f…');

-- result
2 rows
2
snapshots for one observation
B-null, T08. A and B both return 1.

SQL compares NULLs as unknown, so the pair (NULL, fp) never collides with itself. The database is working correctly; the schema is wrong.

rule

Sentinel, never NULL

parent_snapshot_id VARCHAR NOT NULL DEFAULT 'genesis'. One row per stage is the root, and it is deduped by the same constraint as every other edge.

This is the only failure in the experiment that is silent — no error, no warning, just a duplicated root that every downstream join will double.

Six independent runs. B was slower at the median in five (2–35%) and faster in one (8%). The spread across runs is larger than the gap between schemes. Timing does not decide this.

incidental finding

The insert path dominates everything

DuckDB 1.5.6 on Windows binds parameters at roughly 4 ms each. A 20-row × 62-column insert costs 2 485 ms parameterised, 27 ms as literals, and 73 ms via COPY.

implication

Choose the load path before the id

The harness uses literals for the fact insert (numeric-only columns, escaped). In production this is a COPY or appender decision, and it is worth 90× more than the id scheme.

A derived id is a function of its parent. Correct a capture in the middle of history and every later id changes — so the one case A was supposed to protect is the case it fails.

Neither scheme gives address stability under history edits. That is not a defect of the id; it is a category error. The id records lineage. The observation time records address.

12 / recommendation

Take the ULID. Stop treating it as an address.

All 15 idempotency, integrity and scale checks pass for both schemes. The only measured difference that survives scrutiny is that A reproduces ids on an exact replay — a scenario that a backfill immediately invalidates.

So the tie is broken on the properties that remain: shorter key, time-sortable, no dependence on chain position, and no hash of the parent to reason about.

cost accepted

+6.2% storage  ·  ≈+10% median insert (2–35% across six runs)  ·  −11 bytes per id

four conditions, non-negotiable

01  parent_snapshot_id NOT NULL DEFAULT 'genesis'
02  UNIQUE (parent_snapshot_id, content_fingerprint)
03  Reports pin (stage_id, observed_at); no stored snapshot_id outside the warehouse
04  CI asserts a rebuild reproduces the (stage, observed_at) → content map

Buy the 6% storage. Delete the assumption that a row id is a permanent address.

13 / what ships

The schema, and the one rule that makes it idempotent.

CREATE TABLE competition_snapshot (
  snapshot_id          VARCHAR PRIMARY KEY,
  parent_snapshot_id   VARCHAR NOT NULL
                       DEFAULT 'genesis',
  stage_id             VARCHAR NOT NULL,
  content_fingerprint  VARCHAR NOT NULL,
  observed_at          TIMESTAMP NOT NULL,
  accepted_at          TIMESTAMP NOT NULL,

  UNIQUE (parent_snapshot_id, content_fingerprint),
  UNIQUE (stage_id, observed_at)
);

-- the address a report is allowed to store
-- (stage_id, observed_at) — reproducible from raw
-- publish: one transaction, no partial state
BEGIN;
  -- 1. header, deduped by the edge
  INSERT INTO competition_snapshot (...)
  VALUES (...)
  ON CONFLICT (parent_snapshot_id,
               content_fingerprint)
  DO NOTHING;

  -- 2. fact rows only if the header is new
  INSERT INTO fact_team_snapshot ...;

  -- 3. checkpoint, in the same commit
  INSERT INTO checkpoint ... ON CONFLICT ...;
COMMIT;

The pipeline compares the fingerprint to the checkpoint before opening the transaction — a 5 ms no-op. The constraint is the last line of defence, not the first.
