The question the schema answers

A number without a time
is a rumour.

The source publishes no timestamp in the page, the JSON feed, or the response headers. One sweep is twelve requests, not one instant. And a re-fetch can return exactly the bytes we already have.

So the warehouse stores an observation, not a value: a header row that says when, a fingerprint that says what, and facts that say which teams.

Each of the seven tables answers one of those questions. Nothing is stored that cannot be checked by a constraint, a key, or a query that returns bad rows.

The claim

The schema is not a container for numbers. It is the argument that the numbers are comparable.

What
60 measures per team in the feed, 30 more in the league table, one row per team per observation.
When
observed_at is the earliest capture in the sweep; capture_span_seconds says how long the sweep took.
Same?
content_fingerprint is a SHA-256 of the canonical rows. Equal fingerprints mean one observation, not two.
Why it holds
A key, a constraint, and a transaction each answer a question the loader could forget to ask.
One example

Twenty teams, 60 measures each, captured between 10:00:00 and 10:00:14 UTC. The header stores that instant and the 14-second span; the facts store no time at all; the fingerprint decides whether this sweep is already in the table.

Three questions, asked of every row. The next two pages define every word used to answer them.

The words, part one

The words about a row.

TermWhat it means here
GrainWhat one row means. fact_team_snapshot is one team in one snapshot; a table has exactly one grain.
Primary keyThe column or pair that makes a row unique. (snapshot_id, whoscored_team_id) is the fact tables' primary key.
Natural keyA key built from values that already exist. The stage address (tournament, season, stage, observed_at) is natural.
Surrogate keyA value invented to name a row. snapshot_id is one: it carries no meaning and is never reused.
Foreign keyA column that must match a key in another table. A fact row's snapshot_id must exist in the header.
UNIQUEA constraint that no two rows share the listed values. The header has two, doing different jobs.

NOT NULLThe column must have a value. parent_snapshot_id is NOT NULL because NULL would break its UNIQUE.
Grain first

Two grains in one table cannot be repaired by a query later. That is why the header, the team facts and the table facts are three tables, not one.

Eight words. The next page has ten more, about history.

The words, part two

The words about history.

TermWhat it means here

Read the grain

The two fact tables are the only tables a consumer reads. The other five explain how those rows got there, and whether to trust them.

The header

The header is a claim,
not a container.

CREATE TABLE competition_snapshot ( snapshot_id VARCHAR PRIMARY KEY, parent_snapshot_id VARCHAR NOT NULL DEFAULT 'genesis', whoscored_tournament_id INTEGER NOT NULL CHECK (whoscored_tournament_id > 0), whoscored_season_id INTEGER NOT NULL, whoscored_stage_id INTEGER NOT NULL, content_fingerprint VARCHAR NOT NULL, observed_at TIMESTAMPTZ NOT NULL, accepted_at TIMESTAMPTZ NOT NULL, capture_span_seconds DOUBLE NOT NULL CHECK (capture_span_seconds >= 0), run_id VARCHAR NOT NULL, UNIQUE (parent_snapshot_id, content_fingerprint), UNIQUE (whoscored_tournament_id, whoscored_season_id, whoscored_stage_id, observed_at) );

TIMESTAMPTZ is the short spelling of TIMESTAMP WITH TIME ZONE, the exact type in the file.

One clock, one row

Forty fact rows never need to agree on a time, because none of them stores one.

snapshot_id
Opaque name, minted by the publisher. The facts join on this and nothing else.
parent_snapshot_id
Previous accepted snapshot for the same stage, or 'genesis'. It makes the history an edge, not just a list.
observed_at
Earliest capture time in the sweep. This orders history and picks "latest".
accepted_at
When the transaction committed. Audit only; it never orders anything.
fingerprint
SHA-256 of the canonical rows, plus the canonical_version that encoded them.
span
How long the sweep took. Above 180 seconds, the attempt is retried rather than accepted.
provenance
run_id, whoscored_page_url, is_opta: which run, which page, whose data.
The two UNIQUEs are the whole idempotency argument: one observation per instant, one content per parent edge.

Decision 02 · history

A correction is a new row,
not an edit.

Rejected · update in place

The old value disappears

A correction and a fresh observation become indistinguishable. No query can prove what the table said yesterday.

Rejected · SCD2

Two rows and a validity interval

Correct, and it needs a writer that closes the previous version on every change. A late correction then rewrites an interval that was already published.

Chosen · append-only snapshot

Every observation is its own header

A correction arrives with a later observed_at. The old row stays readable, and nothing is closed or rewritten.

Afp 11…
Bfp 22…
A againfp 11…

The third row has the same fingerprint as the first and a different parent. Reusing the first row would erase the fact that B happened.

In practice

No statement in the pipeline updates a header or a fact. The only UPDATEs touch ingestion_run and pipeline_checkpoint, which are current state, not history.

The edge

UNIQUE (parent_snapshot_id, content_fingerprint) allows A→B→A and refuses A→A under the same parent.

The parent pointer is what makes "what did this replace?" a join instead of an assumption about row order.

Decision 03 · keys

The address is natural.
The name is not.

-- the address a report cites UNIQUE (whoscored_tournament_id, whoscored_season_id, whoscored_stage_id, observed_at) -- the name the facts join on snapshot_id VARCHAR PRIMARY KEY -- 'snap_' + 32 hex characters FOREIGN KEY (snapshot_id) REFERENCES competition_snapshot(snapshot_id) PRIMARY KEY (snapshot_id, whoscored_team_id)

Two identities for one row: one a reader can reproduce, one the database can join on cheaply.

Natural address. Four columns identify an observation without asking permission from a generated id. A rebuild can mint a different snapshot_id and still produce the same address and the same fingerprint.

Surrogate name. The id is minted by the publisher, so two writers cannot collide on it, and a fact row carries 32 characters instead of four columns.

Why VARCHAR. Ids are built by concatenation — run_, snap_, replay_ — and read by humans in logs and errors. Nothing does arithmetic on them.

Why the source ids stay INTEGER. Tournament, season, stage and team are the source's numbers. Making them text would hide which values we invented and which we received.

The composite

(snapshot_id, whoscored_team_id) is the grain as a constraint: one team, once, per snapshot.

Note: ADR 0001 calls snapshot_id a ULID, while publish.py mints a UUID4 hex string. Both are opaque text; the code is what runs.

Decision 04 · 60 and 30

Ninety columns is a contract.
1,800 rows is a lookup table.

Every column is nullable. A missing measure is NULL; a real zero is 0 (ADR 0002).

Why 60, not 57

The feed sends 57 raw columns. Nine repeat apps or shots across sections, leaving 48 unique; add three rating columns and nine rankings and the count is exactly 60.

Decision 05 · enforcement

A rule the database
cannot forget.

Declared in the DDLWhat it makes impossible
FK on both fact tablesa fact row whose header does not exist
UNIQUE (parent, fingerprint)the same content twice under one parent
UNIQUE (stage, observed_at)two observations claiming one instant
CHECK (measure >= 0)a negative count, rating or percentage
CHECK (outcome IN …)an eighth run outcome the CLI cannot handle
NOT NULL on identitya fact with no team, or a snapshot with no run
PRIMARY KEY everywheretwo rows with one identity

Each row has a test in tests/test_schema.py; the assertion rules have one per trap in tests/test_assertions.py.

NULL is not FALSE. A CHECK passes when its expression is TRUE or NULL. It fails only on FALSE.

NULL >= 0 -> NULL CHECK passes 0 >= 0 -> TRUE CHECK passes -1 >= 0 -> FALSE CHECK fails

That is deliberate. A missing measure is not a negative one, so the column stays nullable and the constraint still rejects a real negative.

What Python still owns

Rules that need more than one row: the cohort size, the nine captures, the home/away sums. Those are assertions, not constraints.

Why not Python only

A constraint runs on the insert path of every writer, including a hand-written INSERT from a notebook. A Python check runs only where someone remembered to call it.

A constraint is evaluated on one row at insert time. Anything that compares rows is a query, and this schema puts those queries in sql/002.

Decision 06 · idempotency

Two writers cannot both win
a race they never entered.

INSERT INTO competition_snapshot (…14 columns…) VALUES (?, ?, ?, ?, ?, ?, ?, 1, ?, ?, ?, ?, ?, ?) ON CONFLICT (parent_snapshot_id, content_fingerprint) DO NOTHING RETURNING snapshot_id -- no row returned means: this content -- already exists under this parent SELECT snapshot_id FROM competition_snapshot WHERE parent_snapshot_id = ? AND content_fingerprint = ?

One statement both writes and decides. The conflict target is the declared UNIQUE, not a guess.

StepWriter AWriter B
look up parent + fingerprintnot foundnot found
insert … on conflict do nothingrow returnedno row
outcomeacceptedexisting id, no_change

A check-then-insert has a gap between the two statements. Both writers pass the check, then one fails at insert time with a constraint error the caller has to interpret.

Here the database decides, and the second writer gets a normal outcome instead of an exception.

The NULL trap

A UNIQUE index treats two NULLs as different. parent_snapshot_id is NOT NULL DEFAULT 'genesis' so that the guard cannot silently stop working.

Pinned by test_null_parent_is_not_a_uniqueness_guard and test_duplicate_parent_and_content_is_rejected.

Decision 07 · atomicity

Six statements. One commit.
No half snapshot.

BEGIN run 22 assertions -- TEMP tables only INSERT header -- ON CONFLICT … RETURNING INSERT 20 team facts -- one statement INSERT 20 table facts -- one statement UPSERT checkpoint -- last id, fingerprint UPDATE run outcome -- accepted | no_change COMMIT except BaseException: ROLLBACK raise # COMMIT never lives in finally
Why not finally

After an aborted statement, a bare COMMIT does not raise and commits nothing. The success path commits; the failure path rolls back.

Write, audit, publish. The raw payloads and their ledger rows are committed first, by land_stage. The audit reads those bytes, and only then is the warehouse touched.

A crash between…What survives
header and factsnothing: the transaction rolls back
facts and checkpointnothing: the checkpoint is inside the transaction
checkpoint and run outcomenothing: the run outcome is the last write before COMMIT
process start and publisha running row; reconcile() resolves it
Rejected

A staging table plus a second load. It adds a copy, a cleanup job, and a window in which the staging rows and the warehouse disagree.

The promise

There is no state in which a reader sees a header without its facts, or facts without a run outcome: either the whole observation committed, or none of it did.

The alternative to write-audit-publish is auditing after the insert, which means a bad observation is already history when the rule fires.

Decision 08 · validation

A rule is a query that
must return nothing.

0
rows returned → pass
n
rows returned → fail

The candidate and its provenance are loaded into TEMP tables. Each rule is a query over those tables plus the previous accepted snapshot; the failure carries its rows.

A test framework asserts that code behaved. This asks whether the data is coherent, and it can only be answered in SQL because the rules compare rows: nine captures, twenty teams, home plus away.

In the file

sql/002_assertions.sql is deliberately comment-only, so the migration runner can execute it and the validator can read the same file.

BLOCK · 14 rules

Stop the publish

The data is incoherent or impossible. A human or a config change is needed: cohort size, ranking range, negative measures, a missing team, a non-increasing appearance count.

RETRY · 7 rules

Fetch again

The source may be mid-update: mismatched team sets, split totals that do not add up, a slow sweep, a missing standings view.

WARN · 1 rule

Record and continue

A duplicate rank is suspicious, not impossible. The snapshot is kept and the finding is recorded.

BLOCK and RETRY both stop this attempt; only the caller's retry policy differs. WARN returns a failure without blocking.

Decision 10 · two shapes of rule

Two rules that are not
about a single row.

The cohort · A1 · BLOCK

14 teams short
SELECT count(*) AS actual, (SELECT expected_teams FROM _assert_run) AS expected FROM _assert_team HAVING count(*) <> (SELECT expected_teams FROM _assert_run)

The expected size comes from the stage registry, not from the payload: 20 for the Premier League, 24 for the Championship, 18 for the Bundesliga, 36 for a UEFA league phase.

A feed with three teams would otherwise parse perfectly and publish an incomplete league.

The duplicate rank · A7U · WARN

record only
SELECT section, view, ranking, count(*) AS rows FROM _assert_rank WHERE ranking IS NOT NULL GROUP BY 1, 2, 3 HAVING count(*) > 1

A7 blocks a rank outside 1..N. A7U catches the other failure: two teams claiming rank 4. It has its own id because one assertion cannot return both a blocking range result and a warning duplicate result.

Why warn

A duplicate rank is suspicious, not impossible. The snapshot is worth keeping; the finding is worth recording.

Both read staged tables, not the warehouse: the candidate is validated before it can become history.

Decision 11 · consumers

Pick the snapshot first.
Join the facts second.

WITH latest AS ( SELECT *, row_number() OVER ( PARTITION BY whoscored_tournament_id, whoscored_season_id, whoscored_stage_id ORDER BY observed_at DESC, accepted_at DESC, snapshot_id DESC ) AS snapshot_rank FROM competition_snapshot ) SELECT h.* EXCLUDE (snapshot_rank), f.* EXCLUDE (snapshot_id) FROM latest h JOIN fact_team_snapshot f USING (snapshot_id) WHERE h.snapshot_rank = 1;

The ordering is observed_at first. accepted_at is only a tie-break inside one instant, so a backfill cannot become latest.

Rejected

A materialized latest table. It must be refreshed on every publish, and between the publish and the refresh it answers with yesterday's state.

The leak test

A team dropped from the newest snapshot does not reappear from an older one. That is the test, and it fails if the join is written first.

Seven plain views: they store nothing. EXCLUDE is DuckDB's way to drop a column from *; PostgreSQL spells the column list out.

Decision 12 · time

Store the instant.
Render the zone at read time.

Sessionstored instant reads asAT TIME ZONE 'Asia/Kolkata'
UTC2026-10-21 10:00+002026-10-21 15:30
Asia/Kolkata2026-10-21 15:30+05:302026-10-21 15:30

Both sessions read the same instant. Before the change, both returned the bare value 10:00, and the second session had no way to know it was UTC.

The guarantee now travels with the file: a notebook, the duckdb CLI, or a BI tool cannot misread it by forgetting a setting.

Cost

Day buckets need an explicit zone: date_trunc('day', observed_at AT TIME ZONE 'Asia/Kolkata'). Python now returns aware datetimes.

CREATE OR REPLACE VIEW v_snapshot_clock AS SELECT snapshot_id, observed_at AS observed_at_utc, observed_at AT TIME ZONE 'Asia/Kolkata' AS observed_at_ist, accepted_at AS accepted_at_utc, accepted_at AT TIME ZONE 'Asia/Kolkata' AS accepted_at_ist FROM competition_snapshot;

The view stores nothing. It is a lens: one instant, two renderings, no second copy of the truth.

Rejected: naive TIMESTAMP plus a session pin; UTC epoch as BIGINT; storing both UTC and IST columns; storing a fixed +05:30 offset.

The test that caught it

The freshness test expected an age near five minutes and got one offset by the host's UTC offset. The fix moved the guarantee from a helper that had to be called into the column type itself.

Eight timestamp columns in sql/001, plus the ledger's applied_at. The session is still pinned to UTC, now as a default rather than the guarantee.

One writer, one file,
read-only readers.

Decision 15 · what is absent

Nothing runs inside the database
except the SQL you send.

No triggers

Nothing fires on insert

DuckDB has no trigger surface. The audit runs before the insert, in the same transaction, instead of reacting after it.

No stored procedures

The rules are readable text

There is no CREATE PROCEDURE. The 22 rules are SQL in sql/002, read by the validator and executed as queries.

No ORM

The schema is the contract

publish.py sends SQL; contract.py owns the column names. No generated layer sits between the code and the DDL.

What replaces itScope
Constraints: PK, FK, UNIQUE, CHECKone row, at insert time
Assertions: A1–A21 and A7Uone candidate, before publish
Views: seven, including freshnessone reader, at query time
Ledger: schema_migrationone file, once

The cost. Nothing enforces a rule you forget to call. A trigger would fire even for a hand-written insert; these rules do not.

The mitigation. publish() is the only function that writes a header or a fact, and it runs every assertion on every attempt. The CLI is its only caller.

A deliberate trade: fewer moving parts in the database, and one code path that has to stay correct.

In practice · after a crash

The database can explain
a crash it did not see.

Reconcile, on the next start

A run left running…Becomes
has a committed snapshot with its run_idaccepted

A normal crash between header and facts cannot leave a running row, because the run outcome commits with the data. Reconcile covers process death before publish, and runs killed from outside.

Why not delete

An abandoned run is evidence about the source. It stays, and the checkpoint counts it.

Freshness, for an operator

age_seconds = CASE WHEN last_success_at IS NULL THEN NULL ELSE greatest(0, date_diff('second', last_success_at, current_timestamp)) END
TOURNAMENT SEASON STAGE AGE_S OUTCOME SNAPSHOTS -- one row per stage known to the checkpoint, -- the snapshots, or the runs

The view unions stage addresses from the checkpoint, the snapshots and the runs, so a stage seen only in one of them still appears.

A stage that exists only in configuration has no row anywhere, so the view cannot show it. That is the honest limit of a view built from data.

Why it matters

A stale stage and a broken pipeline look identical in a table nobody reads. The freshness view is the difference between noticing in five minutes and noticing next week.

age_seconds is NULL until the first success and is clamped at zero, so a clock skew cannot render a negative age.

What this does not prove

That the source behaves the same way next week. That is what the assertions are for, on every run, rather than one afternoon's evidence.

The sweep is an operator tool, not a CI test: CI cannot reach the source. The committed evidence is the table above and the audit's results file.

The rule for all seven

A change needs a measurement that says it is needed, not a preference. Until the trigger fires, the smaller design is the more honest one.

None of these change the grain, the keys, or the assertion vocabulary. They change the engine, the storage, and the team dimension.

Close

The schema is small.
The promises are the product.

It guarantees

Every fact has a header, and every header has one observation time.

The same content cannot be accepted twice under one parent.

A snapshot is readable in full, or not at all.

An edited migration file is refused, not re-run.

It refuses

An incomplete cohort, or a team with no standings row.

A points total above the maximum, or a negative measure.

An orphan fact, a duplicate edge, an eighth run outcome.

A local wall clock pretending to be an instant.
