02/ HOW TO READ THIS

Four habits, repeated
on every slide.

Feynman · explain it simply

Plain words, then an analogy. If the analogy breaks, the understanding is incomplete. Each concept slide carries one.

First principles · derive it

Start from what must be true about the data. Do not start from a tool. The mechanism should be the consequence, not the fashion.

Second order · and then what?

Every decision has a cost that arrives later. Named explicitly: what breaks in six months if we skip this?

Source + recommendation

Every concept ends with a citation and one concrete action. A claim without a source is an opinion; an action without an owner is a wish.

What this deck is

A review of commits ace7897 → b898900, the P0–P7 reports, sql/001–003, and the tests. Written for a developer or an agent joining the project.

What it is not

A live-data review. There is no data/dataderby.duckdb yet and no committed real capture. Every fixture is synthetic. Runtime behaviour on real WhoScored pages is unproven.

Check yourself. Can you say why a review of design and a review of operations are different claims? (One is "the shape is right"; the other is "it survives Tuesday".)

03/ THE PROBLEM

One sentence.
Everything else follows.

“At each accepted observation, the source reports a table of teams and a set of cumulative statistics. Keep every reported state so the same team can be compared with itself across time.”

Property 01

Cumulative, not per-event

Goals-for is a season total. The difference between two snapshots bounds activity; it cannot be attributed to one match.

Property 02

Irregular cadence

Triggers are fixtures finishing. The source publishes late and in batches, so "one row per day" is a lie.

Property 03

Thin, hostile source

No update timestamp, no ETag, no revision id, an anti-bot gate, and possible silent corrections. You cannot ask the source what changed.

Feynman · the photograph

A normal dashboard is a painting: you keep repainting it, and last week's version is gone. This pipeline is a photograph album: every matchday gets a new print, and old prints are never touched. Comparing two prints tells you what changed. Repainting tells you nothing.

05/ THE PIPELINE, END TO END

Six stages.
One direction of flow.

Feynman · the grocery run

Keep the receipts (raw), cook once (parse), taste before serving (audit), then put the dish in the window (commit). If it tastes wrong, you still have the receipts.

First principles

Raw is the only irreplaceable layer. Everything after it is a deterministic function of bytes. That is why replay is possible at all.

Do this

When debugging, walk the arrows backwards. Most errors are visible before the database: a missing capture, a gate page, a drifted column.

Source Databricks · medallion layers · raw, conformed, published; raw is append-only
06/ CONCEPT 01

Raw is the system of record.
The database is derived.

Every payload is written once, with a SHA-256, a path and a run id. Nothing under data/raw/ is ever edited.

Why it matters

If the parser is wrong, you rebuild from bytes. If the parser is right and the database is lost, you rebuild from bytes. Without an immutable landing zone, neither is possible.

Feynman · the lab notebook

You write the experiment down before you interpret it. You may add pages. You never tear one out because the result was inconvenient.

Second order

The backup policy inverts. Back up data/raw/, not the .duckdb file. The first person on call will reach for the database; the runbook has to say otherwise.

Source Databricks · medallion architecture

Check yourself. Why is the hash stored next to the file instead of inside it? (So the check survives a re-encode, and the file stays byte-identical to what the source sent.)

07/ CONCEPT 02

History is a sequence
of snapshots.

One row per team per accepted observation. Never an UPDATE. This is Kimball's periodic snapshot fact, not SCD Type 2.

SCD2 needs UPDATE permission. This table needs INSERT only, which is why the replay guarantee is one sentence.

Feynman · bank statements

Your balance today cannot explain how you got there. The statement lines can. A snapshot is a statement line; "latest" is just the most recent line.

Second order

Storage grows by ~1,240 rows per snapshot, which is nothing. The real long-term cost is the rule that picks "latest". Get it wrong once and every chart drifts.

08/ CONCEPT 03

A snapshot is identified by
its parent and its content.

Three keys are possible. Only one survives a retry, a backfill and a revert.

KeyRetry-safeKeeps a revertSurvives a backfill
content_fingerprint aloneyesno — A→B→A collapsesn/a
A random snapshot_id aloneno — new id each retryyesyes
(parent_snapshot_id, content_fingerprint)yesyesyes — as new rows
Content only · what breaks

The third state is byte-identical to the first, so it is treated as a duplicate. History silently keeps the wrong shape.

Parent + content · what holds

The third node has a different parent, so it is a new observation of the same content. That is exactly what a reverted stat line is.

Feynman · the conversation

“We agree” means nothing without knowing who said it and what it was replying to. The content is the sentence; the parent is the turn in the conversation.

Second order

With content-only keys the bug is invisible for months: the delta series flattens and nobody can tell which observation was swallowed. Measured here, content-only produced 2 rows where 3 were correct.

Source Kimball · periodic snapshots · measured in experiments/id-scheme/
09/ CONCEPT 04

Run it twice.
Get one result.

Idempotent means a retry converges to the same state. Not "usually", not "if the checkpoint survived".

The honest guarantee

Exactly-once delivery across a network is not achievable. At-least-once delivery plus an idempotent write is. Production systems are built on the second.

Feynman · the invoice

If the same invoice arrives twice, the ledger must still show one charge. The invoice number is the claim; the unique constraint is the referee.

Second order

A checkpoint is an optimisation, not a correctness mechanism. Teams that trust "last processed" lose data the first time it is written before the data, or the process dies between the two.

Sources Airflow · idempotent tasks DuckDB · ON CONFLICT 
-- the whole mechanism, in one statement
INSERT INTO competition_snapshot (...) VALUES (...)
ON CONFLICT (parent_snapshot_id, content_fingerprint) DO NOTHING
RETURNING snapshot_id;   -- empty result = the conflict was confirmed

Check yourself. Why is a checkpoint not enough? (Because it can be stale, lost, or written before the data. The constraint is checked on every write, forever.)

10/ CONCEPT 05

The transaction is
the staging area.

Write-Audit-Publish normally needs a staging table. Here, uncommitted writes are already invisible to every reader, so the transaction does the job.

Step 01 · cheap precheck

Fingerprint

If the checkpoint already holds this fingerprint, return NO_CHANGE before opening a transaction.

Step 02 · begin

Write privately

Header, 20 team rows, 20 standings rows. Nobody else can see any of it yet.

Step 03 · audit

A1–A21

Any BLOCK or RETRY failure raises PublishBlocked. The write is already invisible; now it is also discarded.

Step 04 · publish

Commit once

Facts, checkpoint and run outcome commit together. There is no window where a run is "accepted" without data.

# the shape that must not change
con.execute("BEGIN")
try:
    ...
except BaseException:
    con.execute("ROLLBACK")
    raise
else:
    con.execute("COMMIT")

No COMMIT in finally. That is not style; it is correctness.

The DuckDB trap (measured)

A constraint violation aborts the transaction. A later bare COMMIT does not raise — it silently commits nothing. A finally: COMMIT would therefore discard a whole run and report success.

Feynman · taste before serving

Cook, taste, then serve. Do not serve while tasting. The diner (the reader) should never see the half-corrected dish.

Source Dagster · write-audit-publish DuckDB · transactions
11/ CONCEPT 06

Validation belongs in the schema,
not only in the writer.

UNIQUE

The duplicate edge

A replayed observation cannot create a second header with the same parent and content. The database, not the retry logic, decides.

FOREIGN KEY

The orphan fact

A team row without a snapshot is impossible, even if a future script forgets to insert the header first.

CHECK

The impossible value

Negative counts and invalid run outcomes are rejected at write time. A missing measure is allowed and stored as NULL.

The NULL rule that surprises everyone

In SQL, NULL >= 0 evaluates to NULL, not false. A CHECK constraint passes when its expression is NULL. So a missing measure passes the non-negative check, while -3 fails. That is the behaviour we want: missing is honest, negative is impossible.

Feynman · building code

Application validation is a sign on the door. Constraints are the load-bearing wall. A second script, a notebook, or a future you can walk past a sign; nobody walks through a wall.

Second order

A constraint added after launch is a migration with a validation scan. Design them with the table; the cost is paid once, at the cheapest moment.

Source PostgreSQL · constraints · semantics match DuckDB
12/ CONCEPT 07

Refuse to publish
an incoherent sweep.

14 assertions

BLOCK

Permanent or incoherent. Do not try again without a human or a config change.

7 assertions

RETRY

Transient, usually a mid-publish source. Fetch again, then give up.

1 assertion

WARN

Recorded, does not block. A7U: duplicate ranking is suspicious but survivable.

21 + 1

Contract

A1–A21 plus A7U, loaded from a comment-delimited SQL file so it migrates like schema.

-- sql/002_assertions.sql
-- @@A1|BLOCK
-- returns offending rows; zero rows = pass
SELECT ... FROM _assert_candidate
WHERE ...;

The query is the assertion. No framework, no results store, no extra dependency.

Feynman · the smoke alarm

An alarm you have never tested is decoration. Every assertion ships with a fixture that must fail it and one that must pass.

The cohort rule

19 teams out of 20 is not a smaller league. It is a wrong league. The cohort is the unit of publication, so A1 blocks before the transaction can commit.

Do this

For every new assertion, write the trap fixture first. An assertion that never fires is worse than no assertion, because it creates false confidence.

Source dbt · data tests

Check yourself. Why is "one value missing" neither RETRY nor BLOCK? (Store NULL. A NULL is honest; a dropped row is indistinguishable from a team that did not play.)

13/ CONCEPT 08

Pick the snapshot first.
Then join the facts.

All six views rank competition_snapshot per stage, keep rank 1, and only then join. The order is the whole point.

Wrong order

Join, then filter

A team missing from the newest snapshot is resurrected by an older fact row.

Right order

Filter, then join

The snapshot is chosen before any fact is read, so nothing older can leak in.

No-table stage

LEFT JOIN

The teams stay, with NULL standings, rather than disappearing.

Feynman · the class photo

Choose this year's photo first, then label the faces. Label every face you have ever seen and last year's album leaks into this year's.

Second order

Without the rule, "latest" changes with any backfill. A chart redraws itself for no visible reason, and yesterday's number is no longer reproducible.

Source Databricks · gold layer · see also docs/reports/p7-views.md
14/ CONCEPT 09

A delta is derived,
and only where it means something.

The three rules

1. Difference additive measures only. A rating difference is not "rating gained".
2. Emit a row only when the team was in the immediately preceding snapshot.
3. A negative apps delta is a correction, not a match. Flag it, do not hide it.

Feynman · the bank balance

The change in your balance is not your salary. It is the net of everything, including corrections. Useful, but only if you know which transactions sit between the two statements.

Second order

A diff across a missing observation looks like a huge match haul. One gap in the series and every trend chart lies. The gap rule costs a few rows and buys trustworthy trends.

Source Kimball · snapshot facts · v_snapshot_delta

Label it honestly. These are changes between observations, not per-match totals. A comment or a column name should say so.

15/ CASE STUDY · A REAL DEFECT CAUGHT BY P7

The same instant,
two different numbers.

What happened

P7's freshness test expected an age near five minutes and got one offset by the host's UTC offset. DuckDB was binding timezone-aware UTC datetime values into TIMESTAMP columns through the session timezone (Asia/Calcutta). The row said 15:30; the observation was 10:00Z.

The fix

db.connect() now runs SET TimeZone='UTC'. Two tests guard the session, and the freshness test traps a local-time comparison.

Feynman · the shared clock

Two people in different cities agree to meet at "10". They need to agree on the timezone before they need to agree on the place. A timestamp without a timezone is the word "10" with no city.

Second order

Unfixed, ordering and freshness would depend on which machine wrote the row. The failure is silent, appears only on a non-UTC host, and corrupts "latest" without changing a single measure.

The general lesson

Implicit global state is an input: session timezone, locale, working directory, environment variables. Make each one explicit at the boundary, or it becomes a bug with a five-and-a-half-hour delay.

Sources PostgreSQL · date/time types DuckDB · TIMESTAMP

18/ GAP 01 · HIGH

Migrations need a memory,
not just an order.

Today migrate() runs every *.sql file in lexical order and relies on CREATE ... IF NOT EXISTS to make a second run harmless.

What breaks

The first non-idempotent migration: ALTER TABLE, a backfill, a DROP, a constraint change. It either fails on the second run or applies twice. There is no record of what has already run, so recovery is guesswork.

Feynman · the recipe book

A recipe with no checkmarks. You cannot tell whether you already added the salt. With one recipe it is obvious; with ten it is dinner ruined.

Second order

The first schema change is the cheapest one you will ever make. Add the ledger while the history is three files long, not thirty.

a changed checksum means someone edited applied history.

Do this

Add schema_migration(version, checksum, applied_at) before the second migration, not after. Make applied files immutable. Verify the checksum before executing. One file, one change.

19/ GAP 02 · MEDIUM

One writer. That is a rule,
not a suggestion.

Feynman · the bathroom key

One key, one occupant. The second person does not queue inside the room; they wait outside or come back. A lock file left behind is not a lock if the OS releases it when the process dies.

What is already true

lock.py implements a cross-platform exclusive lock (msvcrt on Windows, flock elsewhere). It is tested. What is missing is a caller: the P8 run command that acquires it before touching config.

Second order

Without a caller, two overlapping schedules either crash at the DuckDB file (confusing) or, worse, one retries blindly. The lock turns an ambiguous failure into a named exit code.

Do this

Acquire before config, release in finally, return exit code 5 when held. Open every reader with read_only=True.

Source DuckDB · concurrency
20/ GAP 03 · MEDIUM

Make the type carry
the guarantee.

The UTC fix lives in connect(). That protects every caller that uses it. It does not protect the BI tool, the notebook, or the duckdb CLI.

Option A · today

Naive TIMESTAMP

Small, simple, and correct only while every writer and reader remembers the session rule. The guarantee is tribal knowledge.

Option B · recommended

TIMESTAMP WITH TIME ZONE

The instant is unambiguous at the type level. A client cannot accidentally reinterpret it. Slightly larger, and comparisons need care at DST boundaries.

Option C · fallback

UTC epoch BIGINT

No timezone semantics at all. Perfect for machines, hostile to humans reading the table. Document the unit or it becomes a different bug.

Second order · why this is medium, not low

The pipeline is single-writer and every internal caller uses connect(), so today the risk is contained. The moment a dashboard, an analyst, or a second service opens the file, "the numbers depend on the machine" returns. That is the trigger.

Do this

Decide before the first real capture, while the change is free. There is no committed data to migrate, so the cost is one schema edit and one test, not a backfill.

Source PostgreSQL · timestamp with time zone · the semantics DuckDB follows

Check yourself. If a column is TIMESTAMP and a client in Tokyo reads it, what does the value mean? (Whatever the writer's session meant. The type does not say, so the answer is "it depends".)

21/ GAPS 04–05 · OPERATIONS

A gate that only runs locally
is a habit, not a gate.

Gap 04 · high

No CI

The four gates are real: ruff format, ruff check, mypy main.py, pytest. They run before a commit because a human remembers. That is the failure mode.

Feynman · the fire drill

A drill that only happens when someone feels like it is not a drill. It is a story about a drill.

Do this

One workflow, four steps, on every push. Fail the build on formatting drift, not just on failing tests. Keep the phase reports as artifacts.

Source GitHub Actions
Gap 05 · medium

No schedule, no alert

v_pipeline_freshness computes age_seconds, but nothing reads it on a timer. A freshness view nobody watches is a dashboard, not an alert.

Feynman · the smoke detector

The sensor is installed. The battery and the siren are not. You find out about the fire when you smell smoke.

Do this

Cron + lock + run ledger is enough for one pipeline and nine requests a day. Alert when age_seconds exceeds the expected window. Add an orchestrator when a second source or a cross-pipeline dependency appears.

Source Airflow · best practices
Why not add an orchestrator now? One pipeline, one schedule, one writer. An orchestrator adds a scheduler, a metadata database, a UI and an upgrade path to solve a dependency problem this project does not have yet. The trigger is the second source, not the calendar.
22/ SECOND ORDER

What the gaps cost,
if nothing changes.

6 months · the schema change

A new source column arrives. Without a ledger, the ALTER is applied by hand, or applied twice. The migration gap stops being theoretical on the first Tuesday it is needed.

trigger the second SQL file

12 months · the second reader

A notebook opens the file and gets a different observed_at than the pipeline. Or two schedules overlap and one run dies inside the publish transaction. Both look like "the data is wrong".

trigger the first external client

24 months · the second writer

Analytics reads compete with ingestion. The single-writer model is now a constraint on the team, not a feature. The documented escape is Parquet files or a read replica.

trigger a second writer or read load

Feynman · interest on a loan

A missing migration ledger is not a bug today. It is interest accruing on a loan you have not drawn down yet. The bill arrives when you make the second change, and it is paid in outage time.

The honest reading

None of these mean "rewrite the pipeline". They mean: add the ledger, wire the lock, run the four gates in CI, and decide the timestamp type. Four small changes with four clear triggers.

26/ GLOSSARY

The words this codebase
uses without explaining.

Snapshot

One complete observation of a stage at one instant. Never edited after it is accepted.

Grain

What one row means, in one sentence. "One team per snapshot." If it is ambiguous, every aggregate is.

Idempotent

Running it twice has the same effect as running it once.

Transaction

A group of writes that either all commit or all disappear. Readers never see the middle.

Write-Audit-Publish

Write privately, check the result, publish only if it passes. The transaction is the private area here.

Assertion

A query that returns bad rows. Zero rows means pass. A1–A21 are these.

Contract

A promised shape: 60 team measures, 30 standings measures, in a fixed order.

View

A saved query. Reads like a table, stores nothing.

Delta

The difference between two observations. Only meaningful for additive measures.

Backfill

Adding an observation after newer ones already exist. Older observed_at, newer accepted_at.

Checkpoint

A note about the last successful work. An optimisation; never the correctness mechanism.

Fingerprint

A SHA-256 of the canonical payload. Equal content means an equal hash, regardless of row order.

Foreign key

A rule that a child row must point at an existing parent. No orphan facts.

DDL

The statements that define tables. sql/001_schema.sql is DDL.

TOCTOU

Time-of-check to time-of-use: the gap between "is it there?" and "insert it" where a race fits.

Medallion

Bronze / silver / gold layering: raw, conformed, published. This project's "gold" is a set of views.

The rest is discipline.

What matches production

Append-only history, an edge key, idempotent writes, a transactional write-audit-publish, database constraints, blocking assertions, and a tested consumer contract. These are the patterns the sources describe, implemented at the right size for the data.

What does not, yet

No migration ledger, no CI, no schedule or alert, no run entry point wiring the lock, a timestamp guarantee that lives in a helper, and a parser that has never seen a real page.

BEFORE CALLING IT PRODUCTION

01  Add schema_migration before the second SQL file.

02  Wire lock.py into the run entry point; exit 5 when held.

03  Run the four gates in CI on every push.

04  Decide the timestamp type before the first real capture.

05  Capture one real stage end to end and commit a redacted fixture.

06  Schedule the run and alert on v_pipeline_freshness.

The pipeline already does the hard thing: it remembers. The remaining work is making it remember the same thing on every machine, every time.
