The first number is why we felt ready. The second is why we were not.

201 tests is a real achievement, and it is not the point. Every one of those tests used a payload we wrote ourselves. A green suite proves the code is consistent with the fixtures. It cannot prove the fixtures are consistent with WhoScored.
Act I · What green proved

Our code agreed
with our fixtures.

A test with a payload we wrote proves the parser behaves as we described. It does not prove the source behaves as we described.

Consistency is not contact.

So we did the only thing that answers the question: one live capture, the same code, no special cases.

The distinction matters because it is the difference between "the tests pass" and "the system works". Every assumption in the parser was ours. The capture is how we checked them against someone else's reality.
Act I · The plan

Follow one row.

Manchester City. 26 October. 8 played, 7 won, 21 points. We would find that row on the website, in the feeds, and in the database.

pagefeedsparsevalidatepublishre-run

If the same numbers appear at every step, the pipeline is telling the truth. If they diverge, we have found a bug.

One row is easier to follow than a whole table. City is a good choice: it is first, it has a clean record, and its numbers are small enough to check by eye.

Open the page
like a fan.

The stage page renders the league table in the browser. Twenty teams. Manchester City first.

Act II · Step 2 · The key

The key had
moved.

The feeds need a token that the page mints. We used to read it from require. On the live page, require is undefined.

// what the code asked for
require.config.params.site.gSiteHeaderValue   → undefined

// what the page actually contains
gSiteHeaderValue: '4K1Xf6rVYC7Z9qBwY5esrzATONajPhiKjDUt7gInY5U='

First crack. The capture had not fetched a single feed yet.

The token authenticates the feed request. The site moved from an AMD module global to an inline bootstrap. We now read the HTML first and fall back to the old lookup. A test covers both quote styles and the missing case.
Act II · Step 3 · The feeds

Nine envelopes.
Twenty rows each.

Each feed is JSON. statColumns names the numbers. teamTableStats holds one object per team.

{
  "statColumns": ["apps","goal","shotsPerGame","yellowCard",
                  "redCard","possession","passSuccess","aerialWonPerGame"],
  "teamTableStats": [
    { "name": "Man City", "teamName": "Manchester City",
      "teamId": 167, "apps": 8, "goal": 20, "rating": 7.4,
      "ranking": 1, "isOpta": true },
    … 19 more teams
  ]
}

Summary carries 8 columns. Defensive 6. Offensive 5. Three splits each: nine requests.

This is the shape the parser consumes. The column list is the contract: if the source renames or drops a column, the parser refuses the payload instead of silently storing nulls. City's row is the same one we saw in the table, now in machine form.
Act II · Step 4 · The table

Ten fields.
Three splits.

Standings are not in the feeds. They are read from the page. Each team gets one row per split: overall, home, away.

SplitPWDLGFGAPts
Overall870120921
Home440011612
Away4301939

Notice the identity: home + away = overall, in every column. It will matter in Act III.

This identity is the reason the league table is checkable. A team cannot play four home matches and four away matches and somehow have played eight. When the three tables are copies of each other, this identity fails loudly.
Act II · Step 5 · The shape

Nine feeds
become sixty measures.

summary defensive offensive shared: apps, shots, rating ranking

One naming rule keeps them apart: section + split + measure. apps becomes apps_overall, apps_home, apps_away. goal becomes summary_overall_goal.

The prefix is not decoration. Two sections can both report a number called "goals"; without the section in the name one would overwrite the other. Shared measures are owned once and stored per split, so a disagreement between sections is an error, not a silent overwrite.
Act II · Step 6 · The write

One header.
Forty facts.

The snapshot header is the parent. The 20 team rows and the 20 standings rows point at it by foreign key.

TableRowsGrain
competition_snapshot1one observation of the stage
fact_team_snapshot20one team, 60 measures
fact_standings_snapshot20one team, 30 measures

One transaction. Either all of it lands, or the database does not change at all.

A half-written snapshot is worse than no snapshot: a chart would read a partial table as the truth. The header and the facts commit together. The header also carries the observed time, the source flag, and a 64-character content fingerprint.
Act II · Step 7 · Look again

Run it twice.
Write once.

A second capture returns the same content. The fingerprint matches, so the publisher writes nothing.

Run 1 · accepted

new fingerprint

1 header, 20 + 20 facts

checkpoint: accepted

Run 2 · no_change

same fingerprint

checkpoint: no_change

We measured it. The table still held one snapshot after the second run.

The fingerprint is over content, not capture time. If it included the time, every retry would look like new data and the history would fill with duplicates. Content-only identity is what makes a retry free and a correction visible.
Act III · What broke

That is the story
we expected.

The first run did not follow it. Four assumptions failed. One of them failed silently, and only the database noticed.

The next seven slides take them one at a time.

Each problem follows the same shape: what I expected, what happened, why nothing stopped it, how we found it, and the proof that it is fixed. The order is the order we hit them.
Act III · Problem 1 · The tab

Home looked
exactly like Overall.

I expected

Three different tables. City plays 4 at home, 4 away, 8 overall.

What happened

Three identical tables. City shows 8 played in all three.

No error. No warning. The capture looked successful.

This is the most dangerous kind of bug: the run completes, files are written, and the data looks plausible. Nothing in the capture path compares the three views, so the duplication survives until validation.
Act III · Problem 1 · Why

The click
never happened.

The selector asked for data-source="Home". The page uses data-source="home". Zero matches.

# the code, before
selector = f'a.option[data-source="{view.title()}"]'
toggle = page.locator(selector)
if toggle.count():          # 0 matches for "Home"
    toggle.first.click()       # so this line never ran
items = page.evaluate(STANDINGS_JS)   # read Overall again

A guard that protects an action also hides the absence of the action.

The `if` was there to handle stages without a table. It did its job: no exception. But it also turned "the selector is wrong" into "nothing to do". A missing match should have been a failure for a stage that declares a league table.
Act III · Problem 1 · The catch

The database
said no.

A20 says home plus away must equal overall. With three copies of Overall, City had 16 played instead of 8.

SplitPlayedWonPoints
Overall (copied)8721
Home (copied)8721
Away (copied)8721
home + away161442

The assertion did not prevent the bug. It prevented the bug from becoming history.

This is the moment the assertions earned their keep. The capture had no idea it was wrong. The publish transaction ran A1-A21, A20 compared the splits, and the write was refused. The bad data never reached the warehouse.
Act III · Problem 1 · The fix

Lower case.
Then wait for the change.

The selector now matches the page. The capture waits for the table to update before reading it.

SplitPWGFGAPts
Overall8720921
Home4411612
Away43939

Proof: home + away = overall, and A20 passes on the real capture.

The fix is two lines: the selector uses the page's own value, and the read waits long enough for the table to re-render. The proof is not "it looks different"; it is the same identity that caught the bug now holding on live data.
Act III · Problem 2 · Identity

Two names.
One team.

The feed sends name: "Man City" and teamName: "Manchester City". The parser refused the row because they differed.

The feed

Man City — short label

Manchester City — full name

The standings

Manchester City — the same full name

So the full name is the key.

We store teamName and ignore the label. The row is the same team, not a conflict.

The old check was well intentioned: two names for one team usually means a data problem. Here the source is telling us one is a display label and one is the identity. The standings table agrees with the full name, so that is the one the warehouse keeps.
Act III · Problem 3 · Validation

The page shouts.
The database whispers.

Form arrives as WWWWWL. The validator only accepted lower-case wdl, so it rejected a perfectly good row.

# before
form = raw.form.strip()        → "WWWWWL"
if char not in "wdl": reject   → rejected

# after
form = raw.form.strip().lower()  → "wwwwl"

One normalisation at the boundary; everything downstream stays in one case.

The data was correct. Our expectation about its case was wrong. The fix is at the boundary, not in the validator: the validator stays strict, and the parser hands it the canonical form.
Act III · Problem 4 · The transport

A 200
that means 404.

Plain HTTP to the feed returns status 200 and an HTML page: "The page you requested does not exist."

HTTP/1.1 200 OK
content-type: text/html
oc-orchestrator-trace: {"FINGERPRINT":true, ...}
<!DOCTYPE HTML ... "The page you requested does not exist in WhoScored.com" ...

Every status-code check passes. The body is the lie.

This is the scariest finding. A 200 that means "not found" defeats the retry policy, which only classifies 403 and non-200 codes. The response is accepted as a body and then rejected later as a gate page. The status code alone cannot be trusted; the body must be validated.
Act III · Problem 4 · Why

The session
is the key.

The same URL returns JSON when the site's own page calls it. Copying the browser's cookies into curl did not help.

Plain HTTP

200, HTML shell, no data

In the page

200, JSON, 20 teams

The verified browser session is the transport, not just the credential. That is why dataderby run cannot fetch live feeds yet. Tracked as #14.

We tried the obvious workaround first: export the cookie jar and the user agent, then call the endpoint with curl. Same shell. The site ties the feed to a session that only its own page can create. The capture script works because it fetches inside that page. Production needs the same transport, which is a deliberate change with browser lifecycle and pacing to solve.

Why this matters
on a Saturday.

corrections

A club does not need a perfect pipeline; it needs one it can argue with. When a number looks wrong, the analyst should be able to say which observation it came from, when it was captured, and whether it was corrected. That is what the snapshot and the raw bundle buy.
