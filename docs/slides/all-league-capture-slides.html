Why another sweep

One row proved
the parser. Not the rules.

The first live capture followed one team in one league. It answered a narrow question: do real bytes parse? Yes.

It left the important question open. Does the contract still hold when the league has 18 teams, or 36? When a club has a points deduction? When a competition publishes no data at all?

So what

A green test suite on one row is a claim about that row. Twelve leagues is a claim about the model.

What a feed is

A page for people.
JSON for the pipeline.

The stage page renders a league table. Underneath it, the site calls a JSON endpoint for the team numbers.

We call that endpoint nine times: three sections — summary, defensive, offensive — each in three splits — overall, home, away.

page → token → 9 calls summary overall | home | away defensive overall | home | away offensive overall | home | away

The same envelope every time; only the column list and the numbers change.

{ "statColumns": ["apps", "goal", "rating", …], "teamTableStats": [ { "teamName": "Manchester City", "teamId": 167, "apps": 8, "goal": 20, … } , … 19 more teams ] }

statColumns says which numbers are present. teamTableStats holds one object per team.

A missing column is schema drift. The parser refuses the payload instead of storing nulls.

Sixty measures per team come from these nine payloads. The page's league table is a separate source, read from the browser.

What an assertion is

A rule that looks
for bad rows.

Before a snapshot is published, the pipeline runs 21 SQL checks. Each one asks a question and returns the rows that break it.

0
rows returned → pass
n
rows returned → fail

The checks are numbered A1–A21. The number is just an id; the rule is the sentence next to it.

Action · BLOCK

Stop the publish

The data is incoherent or impossible. A human or a config change is needed.

Action · RETRY

Fetch again

The source may be mid-update. Retry, then give up.

Action · WARN

Record, keep going

Suspicious but survivable. It does not stop the snapshot.

A19 and A20, later in this deck, are two of these rules. They check the league table's arithmetic.

Finding 01 · what the pipeline did

Two rules refused
the table.

Rule A19 · BLOCK

Points from wins and draws

points = 3 × won + drawn

Southampton: 20 = 24. Fail.

Rule A20 · RETRY

Points split adds up

points_home + points_away = points_overall

Southampton: 16 + 8 = 20? No, 24. Fail.

Both rules live in sql/002_assertions.sql.

The good part

Nothing was written. The bad table never became history. The assertions did their job.

Blocking was correct behaviour given the rule. The rule was the problem.

We had written that points are a function of wins and draws. True for most rows; false for a club with a deduction.

A RETRY would not help: the deduction is permanent until it is rescinded.

Finding 01 · why the rule was wrong

A deduction is
not a mistake.

Clubs can be docked points. The league table reports the result. The wins and draws stay the same; the total moves down.

The deduction applies to the overall total. Home and away keep their own points, because the deduction is not a match result.

The distinction

Points are reported, like goals. They are not derived, like goal difference.

24
calculated from 7W 3D
20
reported by the table

The −4 is the fact. The arithmetic is the model's opinion.

A deduction is rare, permanent, and invisible to an arithmetic check. Rare is not the same as impossible.

Finding 01 · the fix

Points are reported.
Not calculated.

Before · A19

Equality

points = 3*won + drawn. Any deduction is impossible.

Before · A20

Points summed

points_home + points_away = points_overall. A deduction breaks it.

After · A19

Only impossible totals

Block if points > 3*won + drawn or below zero. A lower total is allowed.

After · A20

Games and goals only

Played, won, drawn, lost, goals for and against still sum. Points are excluded.

Changed: sql/002_assertions.sql. Pinned by tests/test_assertions.py: a 4-point deduction passes; an impossible total still blocks.

Finding 01 · what we record

Allow it.
Don't hide it.

{ "team_id": 18, "name": "Southampton", "points": 20, "calculated": 24, "delta": -4 }

Recorded by the sweep, next to the stage result.

Why record it? A deduction changes a table, a ranking, and a story. It should be visible without reading the source.

What is missing? The publish contract now accepts it silently. Recommendation: a WARN rule (recorded, not blocking), or a view named v_points_adjustments (a saved query that lists them).

Principle

Allow the fact; surface the exception. Those are different jobs.

Southampton's −4 is the only adjustment across the 11 accepted leagues.

Finding 03 · a trap for the next client

Every feed
says HTML.

HTTP/1.1 200 OK content-type: text/html; charset=utf-8 { "teamTableStats": [ … 20 teams … ], "statColumns": [ … 8 names … ] }

108 of 108 responses. The body is always JSON.

Why nothing broke. The parser validates the envelope, not the header. It never asked the server what it had sent.

Why it matters. A future client that trusts Content-Type will reject valid payloads, or parse an HTML error page as if it were data.

Rule

Validate the body. The header is a claim, not a guarantee.

Recorded so the next integration does not "fix" the feed by adding a header check.

Why the scheduled command is not ready

The same URL.
Two different answers.

Path A · the sweep

Ask from inside the page

A browser opens the site. The nine feeds are called by the page itself. The session is the one the site just created.

browser page → fetch(feed URL) → 200 JSON 20 teams, 8 columns ✓
Path B · dataderby run

Ask from Python

The command uses a normal HTTP client, like any backend job. The same URL, no browser page, no verified session.

python HTTP → fetch(feed URL) → 200 HTML "The page you requested does not exist" ✗
A 200 that means "not found" is the trap. The status code is fine; the body is an error page.

The open item, in full

What #14 is.

GitHub issue #14

Title: "Fetch feeds through the browser session; curl returns the site's 404 shell."

What it changes: the two commands an operator runs — dataderby run (full pipeline, used by a schedule) and dataderby probe (one summary feed, no writes, a smoke test) — must fetch the feeds the way the sweep does.

Why it is separate: it changes the browser lifecycle and the request pacing, and needs its own tests. The sweep proved the data path; this issue makes it the production path.

github.com/Vr3n/dataderby/issues/14

"curl" is a command-line HTTP client. Here it stands for any normal backend request, as opposed to a request made by the page.

Until it lands

A scheduled run stops at the fetch step. Parsing, validation, and publishing are proven; the fetch is not.

What is not affected

The one-off sweep still works, because it uses the browser path. That is how the evidence in this deck was produced.

Issue numbers are just ids in the repository tracker. #14 is this one, not a priority score.

This is the only item that blocks a scheduled run. The rest are quality or coverage gaps.
